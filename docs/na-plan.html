01

핵심 결정 요약

기획 문서가 “무엇을 만들 것인가”라면 이 문서는 “어떻게 만들 것인가”다. 기획 대비 변경된 결정은 별도 블록으로 표시했다.

항목결정근거
데이터 수집크롬 확장 프로그램웹사이트는 타 사이트 행동을 볼 수 없음
저장소PostgreSQL + IndexedDB서버·클라이언트 역할 분담
압축 위치확장 내부트래픽 세 자릿수 차이
LLM 호출세션 종료 시 1회진입 시 호출 금지
1차 접점웹사이트새 탭 교체는 v2
인증익명 시작 → Lv.5 계정 연결온보딩 마찰 제거
프라이버시전량 서버 전송스토어 심사 리스크 인지함

아키텍처

[확장 프로그램]                      [서버]
  content script
    └ 10초 단위 활동 신호
  service worker
    ├ Raw events        → IndexedDB
    ├ Compression       (5분 알람)

         │

                                        ├ experiences 저장

                                        ├ 감정 갱신
                                        └ 대사 3~4개 생성
                                            │
[웹사이트] ←──── GET /api/state ─────────┘
기획 #15에서 변경
기획Extension → API → PostgreSQL (raw event 전량 전송)
결정압축·세션화를 확장 내부에서 완료 후 전송
압축 없이 전송하면 하루 수만 건 × 사용자 수. 압축 후에는 하루 5~10건. 세 자릿수 차이다. 압축과 세션화는 규칙 기반 결정적 작업이라 LLM도 서버도 필요 없다.

사이트가 확장 데이터를 직접 못 읽는다

chrome.storage.local과 확장 IndexedDB는 확장 전용 샌드박스다. 일반 웹페이지에서 접근할 수 없다. 따라서 사이트는 반드시 서버 API를 경유한다.

진행 중 세션 같은 실시간 데이터가 필요해지면 externally_connectable로 다리를 놓을 수 있으나 v1 제외.

document.addEventListener('scroll', () => count++, { passive: true });

setInterval(() => {
  if (count > 0) {
    chrome.runtime.sendMessage({ type: 'ACTIVITY', scrolls: count });
    count = 0;
  }
}, 10000);

04

세션 판단 규칙

이 세션 하나가 LLM에게 “무슨 일을 했다” 한 문장으로 요약될 수 있는가.

규칙을 더 늘릴지 말지는 이 질문으로 결정한다.

종료 조건 네 가지

function shouldClose(s, now) {
  if (now - s.lastActivity > 30*60*1000)  return 'idle';
  if (contextSwitched(s, now))            return 'switch';
  if (now - s.startedAt > 4*60*60*1000)   return 'maxlen';
  if (dayBoundaryCrossed(s, now))         return 'day';
  return null;
}
조건이유
idle 30분기본 조건
maxlen 4시간상한이 없으면 8시간 코딩이 세션 하나가 되어 요약이 뭉개진다. continued_from을 남겨 서버가 이어붙인다
day 새벽 4시자정 기준이면 새벽 작업이 이틀로 쪼개진다

맥락 전환

function contextSwitched(s, now) {
  const recent = s.events.filter(e => now - e.at < 10*60*1000);
  if (recent.length === 0) return false;

  const newCat = dominantCategory(recent);
  if (newCat === s.primaryCategory) return false;

  const drift = now - firstEventOfCategory(recent, newCat).at;
  return drift >= 10*60*1000;
}

최근 10분이 계속 다른 카테고리면 전환. 10분 유예는 잠깐 이탈했다 돌아오는 것을 안 끊기 위함이다.

예외 A — 보조 도메인 흡수

const COMPANION = ['google.com', 'stackoverflow.com', 'chatgpt.com',
                   'claude.ai', 'developer.mozilla.org'];

검색·문서·AI 도구는 앞선 맥락에 흡수시켜 카테고리 판정에서 제외한다. 기획 #8의 GitHub + ChatGPT + Redis Docs → "Redis 캐싱 구현" 예시가 이 규칙 덕에 성립한다. 없으면 세 개로 쪼개진다.

예외 B — 왕복은 끊지 말고 태그

if (s.switchCount >= 3 && s.durationMin < 60) {
  s.tag = 'scattered';
  return false;   // 끊지 않음
}

GitHub↔YouTube 왕복을 네 개로 쪼개는 대신 scattered 태그를 붙인다. LLM이 “집중이 잘 안 되는 날”로 요약할 수 있고, 성격 축(몰입형↔산만형)의 입력이 된다. 버그를 데이터로 바꾸는 지점.

예외 C — 백그라운드 재생

music.youtube.com, spotify.com은 활성 탭이 아니면 카테고리 판정에서 제외한다. 안 그러면 모든 코딩 세션이 음악 세션이 된다.

전송 필터

function isWorthSending(s) {
  if (s.durationMin < 10)   return false;
  if (s.activityScore < 50) return false;
  if (s.uniqueDomains === 1 && s.category === 'entertainment'
      && s.activityScore < 150) return false;
  return true;
}

세 번째는 영상 필터다. 다만 점수 150 이상은 통과시켜 진짜 강의 시청은 살린다.

결과 — 하루 세션 20~30개 발생 → 전송 5~10개 → LLM 호출 3~5회.

검증 방법

규칙을 더 늘리기 전에 본인 브라우징 하루치를 IndexedDB에 쌓고, LLM 없이 규칙만 돌려 세션 분할 결과를 표로 확인한다. 하루치만 봐도 예외가 두세 개 더 나온다. 지금 앉아서 규칙 스무 개를 만드는 것보다 다섯 개로 시작해 실제 데이터로 튜닝하는 게 빠르다.
05

서버 파이프라인

세션 ≠ 경험

세션은 관측 단위(규칙으로 자동 도출), 경험은 의미 단위(LLM 판단)다. 대부분 1:1이지만 정확히는 N:M이다.

  • 한 경험이 여러 세션에 걸침 — 점심 전후로 이어지는 작업. maxlen 절단은 정의상 경험 하나를 둘로 쪼갠다
  • 한 세션에 여러 경험 — 같은 카테고리 안에서 프로젝트가 바뀌는 경우
저장 방식 결정
기각하루 동안 갱신하다 자정에 저장
결정세션 종료 시 즉시 저장, 요약은 계층으로 쌓음
자정 방식은 감정 실시간이 깨지고, 오늘 데이터를 못 보며, 결정적으로 늦게 도착하는 세션을 넣을 곳이 없다. 세션은 며칠 뒤에 도착할 수 있으므로 시간 기반 저장은 전송 모델과 구조적으로 맞지 않는다.
sessions      확장이 만듦, 규칙 기반      하루 20~30개 (5~10개 전송)
   ↓
experiences   세션 종료 시 즉시 저장       하루 3~5개   ← 원자 단위, 불변
   ↓
threads       같은 작업끼리 묶음           며칠~몇 주
   ↓
memories      점수 넘은 것만               드물게

Experience Engine

세션 종료 시 LLM 1회 호출. 기존 컨텍스트 주입이 필수다. 없으면 아래를 구분하지 못한다.

"TypeScript로 기능을 구현했다"     ← 늘 하던 것
"처음으로 TypeScript를 써봤다"     ← 신규 스킬 획득

프롬프트에 현재 스킬 목록과 최근 경험 3건을 함께 넣는다. 파이프라인이 단방향이면 안 되고 Memory → Experience 역방향 연결이 필요하다.

출력 제약 — 대사는 40자 이내 두 문장. 초과 시 서버에서 절단. 세 줄이 넘으면 화면이 무너진다.

Memory Engine

LLM 재호출 금지. 규칙 점수로 선별한다.

신규 스킬 등장          +50
해당 스킬 첫 시도        +40
3일 이상 공백 후 복귀     +30
세션 길이 평소의 2배      +20
같은 패턴 반복           -30

임계값 초과 → 장기 기억

기억의 입력은 experience가 아니라 thread의 상태 변화다. 기획 #10의 “첫 출시”는 세션 하나가 아니라 몇 주짜리 thread의 완결이다. experience 단위로 기억을 만들면 “Unity 빌드 설정을 수정했다” 같은 게 장기 기억이 된다.

주기

시점처리
세션 종료 시Experience Engine, 감정 갱신, 대사 생성, thread 부착
야간 · 새벽 3시일기 생성, 성격 축 재계산, 레벨 갱신

성격은 세션 하나로 바뀌면 안 된다. 최소 2주 이동평균.

emotions 테이블을 만들지 않는다. 최근 경험 N건에서 매번 계산하는 파생값이며 시간에 따라 감쇠한다. 저장하면 “3주 전의 기쁨”이 남아 이상해진다.

레벨

레벨 = min( f(경험 수, 고유 스킬 수),  가입 후 일수 / 3 )

학습량이 레벨을 올리고, 일수는 하루 몰아치기를 막는 브레이크로만 쓴다. 일수가 단독 변수면 방치 계정이 Lv.60 “동료 AI”가 되어 정의가 깨진다.

레벨 AND 데이터 조건

레벨만으로 게이팅하면 깨진다. 하루 12시간씩 몰아친 사용자가 30일 만에 Lv.30이 되면 searchMemory()가 켜지는데 연결할 과거가 없다.

LLM은 툴이 있으면 부르고, 결과가 빈약해도 지어낸다. 조건 미달이면 툴을 아예 빼야 한다. “데이터 부족” 응답을 돌려주면 그 상태로도 말하려 든다.
function buildTools(level, stats) {
  const tools = [];
  if (level >= 5  && stats.experienceCount >= 5)   tools.push(getTodayExperiences);
  if (level >= 10 && stats.activeDays >= 14)       tools.push(getWeeklyPattern);
  if (level >= 30 && stats.memoryCount >= 20
                  && stats.oldestMemoryDays >= 60) tools.push(searchMemory);
  return tools;
}

새 기능을 즉시 한 번 써서 보여준다. “습관 분석 해금!”보다 훨씬 강하다.

비용 주의 — 레벨이 오를수록 툴과 컨텍스트가 커진다. Lv.50 사용자 1회 호출이 Lv.5의 5~10배가 될 수 있다. 오래 쓴 사용자가 가장 비싼 사용자가 되는 구조이므로 툴 결과에 LIMIT이 필수다.

인증

익명으로 시작한다

확장 설치 시 익명 키를 발급받고 그것만으로 식별한다. 회원가입 화면도 비밀번호도 없다.

chrome.runtime.onInstalled.addListener(async () => {
  const { key } = await fetch(API + '/register', { method: 'POST' })
                        .then(r => r.json());
  await chrome.storage.local.set({ extensionKey: key });
});

온보딩 마찰이 0이고, “AI가 태어났다”는 연출과도 맞는다. 가입 폼부터 뜨면 그 감각이 깨진다. Day 0에 사용자가 하는 행동은 이름 입력 하나뿐이어야 한다.

그대로 두면 DB를 둔 이유가 사라진다

키가 chrome.storage.local에만 있으면 재설치·PC 교체·프로필 초기화에서 전부 유실된다. 서버에 데이터가 살아있어도 찾아올 방법이 없다. “캐릭터 유실 방지”가 DB 도입의 근거였는데 그게 무효화된다.

사이트를 본체로 삼기로 했으므로 사이트가 사용자를 알아볼 방법도 필요하다.

계정 연결을 레벨 언락처럼 다룬다

Day 0    설치 → 익명 키 발급 → 바로 시작
         AI: "..."  → 이름 지어주기

Lv.5쯤   AI: "나 이제 하루를 기억할 수 있어.
              근데 이 브라우저를 벗어나면 다 잊어버려."
         [ 계정 연결하기 ]

첫날 가입 폼을 들이밀면 이탈하지만, 사흘 키운 캐릭터를 잃기 싫어지는 시점에는 사용자가 자발적으로 누른다. 이 요청이 캐릭터의 대사로 나오면 UI가 아니라 서사가 된다.

인증은 구글 OAuth 하나만. 비밀번호 관리·재설정 메일·해싱이 전부 사라지고, 크롬 사용자면 클릭 한 번이다.

기기 분리

기기가 여러 대면 키도 여러 개다. 개발자가 주 사용자라면 노트북과 데스크톱 두 대는 기본이므로 실질적으로 필요하다.

CREATE TABLE devices (
  extension_key  TEXT PRIMARY KEY,
  user_id        UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  label          TEXT,              -- '회사 노트북'
  last_seen_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

이러면 두 기기의 세션이 같은 캐릭터로 합쳐진다. 기획에는 없던 항목이다.

구현 순서 — v1은 익명만 구현하고 계정 연결은 Lv.5 언락으로 붙인다. 다만 users 테이블은 지금부터 계정 컬럼(google_id, email, linked_at)을 갖고 있어야 나중에 마이그레이션이 없다.

chrome.action.setBadgeText({ text: '1' });

v2 — 새 탭 교체 (보류)

보류하되 폐기하지 않는다. 사이트를 먼저 만들면 API가 이미 있어 붙이기 쉽다.

  • 레벨·이름은 우측 상단 구석 — 하루 40번 보는 화면이라 중앙에 크게 두면 사흘이면 질린다
  • 캐릭터와 대사가 정중앙, 대사만 세리프체 — 말하는 존재만 서체가 다르면 “UI가 아니라 누구”가 된다
  • 검색창 필수 유지, 단 대사 아래 배치
  • chrome.topSites로 자주 가는 사이트 복원 — 없으면 “원래 있던 게 사라졌다”고 느낀다
document.querySelector('input').focus();            // 최우선
chrome.storage.local.get('dialogue').then(render);  // 그 다음

Ctrl+T 직후 타이핑하는 사용자가 첫 글자를 놓치면 안 된다.

데이터 모델

experiences는 절대 UPDATE 하지 않는다.

나머지는 전부 여기서 재계산 가능한 파생 테이블로 둔다. 그러면 나중에 규칙이나 프롬프트를 바꿔도 되돌릴 수 있다. thread_id 부착 1회만 예외다.

테이블성격비고
users / devices원본익명 키 + 구글 계정
characters파생 캐시툴 게이팅이 JOIN 없이 한 행만 읽도록
sessions원본PK = 클라이언트 UUID
experiences원본 · 불변모든 파생의 근원
experience_skills원본조인 테이블
user_skills파생 캐시재계산 가능
threads파생status 전이가 기억 트리거
memories파생forgotten_at 마킹, 삭제 안 함
personality_snapshots파생 · append갱신 아님
daily_logs파생prompt_version으로 재생성
dialogues캐시길이 CHECK 제약

설명이 필요한 결정

sessions.id를 클라이언트가 만든다. 서버 생성 UUID면 재시도 시 같은 세션이 두 번 들어간다. 클라이언트 UUID를 PK로 두면 ON CONFLICT DO NOTHING 한 줄로 멱등성이 끝난다.

emotion 컬럼 대신 experiences.outcome. success / partial / stuck / explore 네 개가 감정의 재료다. stuck 3연속이면 답답, success면 성취. 감정 자체는 조회 시점에 계산한다.

memories.forgotten_at은 삭제가 아니라 마킹. Lv.80 망각이 켜져도 데이터는 남고 검색 결과에서만 빠진다. 성능 최적화가 서사와 일치하는 드문 지점이다.

daily_logs.prompt_version이 숨은 핵심. 일기 프롬프트를 개선하면 과거 일기를 전부 재생성할 수 있다. experiences를 불변으로 둔 덕분에 가능하다.

리스크

스토어 심사. 방문 기록 전체를 외부 전송하는 확장은 Chrome Web Store Limited Use 정책 대상이다. <all_urls> 권한과 겹쳐 심사 난이도가 높다. 공개 배포 시 개인정보처리방침 필수.

품질 리스크(프라이버시와 별개). 은행·의료·DM·비밀번호 입력창의 이벤트는 경험으로 쓸모가 없으면서 LLM 토큰만 소모한다. 최소 도메인 blocklist는 비용 절감 장치로 권장한다.

초반 이탈. Lv.1은 말도 못 하고 보여줄 것도 없다. 레벨 커브를 앞으로 당겨 Lv.5를 사흘 안에 도달시키는 것으로 대응한다.

LLM 환각. 데이터가 빈약해도 그럴듯하게 지어낸다. 툴 게이팅과 출력 스키마 검증으로 대응한다.
