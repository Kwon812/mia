사이트가 확장 데이터를 직접 못 읽는다

chrome.storage.local과 확장 IndexedDB는 확장 전용 샌드박스다. 일반 웹페이지에서 접근할 수 없다. 따라서 사이트는 반드시 서버 API를 경유한다.

진행 중 세션 같은 실시간 데이터가 필요해지면 externally_connectable로 다리를 놓을 수 있으나 v1 제외.

03

확장 프로그램

MV3 핵심 제약

서비스 워커는 30초 놀면 죽는다. 메모리에 아무것도 남기지 마라.

이 원칙 하나에서 아래 규칙이 전부 파생된다.

금지대체
setIntervalchrome.alarms
전역 변수 버퍼IndexedDB / chrome.storage.local
응답 대기 중 상태 유지pending 기록 + 재시도 알람

알람 주기

알람주기근거
sessionCheck1분5분이면 종료 판정이 30~35분에서 흔들림
retry10분더 짧으면 서버 다운 시 복구 방해. 전송 실패분과 원본 업로드를 함께 맡는다

둘뿐이다. compress는 줄이는 게 없어서, diary는 일기가 서버 야간 배치로 옮겨가서 없앴다. 구버전이 등록해둔 잔재는 기동 시 chrome.alarms.clear로 정리한다.

content script의 활동 보고는 setInterval 10초 — 페이지 컨텍스트라 죽지 않는다.

알람이 사라지는 경로가 있다 — 확장 비활성화 후 재활성화처럼 onInstalled도 onStartup도 발화하지 않는 경우다. 그러면 rawEvents 만 무한히 쌓이고 세션은 영영 마감되지 않는데 화면상 아무 증상이 없다. 그래서 워커가 깨어날 때마다 알람 존재를 확인하고 없으면 다시 등록한다.

이벤트 수집

탭 전환·URL 변경은 서비스 워커에서 chrome.tabs로 직접 잡지만, 클릭·스크롤·키 입력은 content script가 필요하다. 원본 이벤트를 보내지 않고 “10초 동안 살아있었다”는 신호만 보고한다.

let scrolls = 0, clicks = 0, keys = 0;
document.addEventListener('scroll',  () => scrolls++, { passive: true });
document.addEventListener('click',   () => clicks++,  { passive: true });
// 키 "횟수"만 센다 — 어떤 키인지는 절대 읽지 않는다 (키로거 금지)
document.addEventListener('keydown', () => keys++,    { passive: true });

setInterval(() => {
  const playing = isMediaPlaying();   // 보이는 탭에서 video/audio 재생 중
  if (scrolls === 0 && clicks === 0 && keys === 0 && !playing) return;

  chrome.runtime.sendMessage({
    type: 'ACTIVITY', scrolls, clicks, keys, playing,
    url: location.hostname,
    visible: document.visibilityState === 'visible',
    // 의도 컨텍스트 — 무엇을 읽고 무엇을 검색했나
    title: document.title, path: location.pathname, query: extractSearchQuery(),
  });
  scrolls = clicks = keys = 0;
}, 10000);

초판에는 스크롤 수만 있었다. 제목·경로·검색어를 함께 보내는 것이 판정 품질을 갈랐다 — 같은 localhost라도 제목이 다르면 다른 프로젝트고, 검색어 반복 횟수가 stuck 판정의 유일한 근거다. 입력 필드 값·페이지 본문·키 내용은 읽지 않는다.

전송 안정성

async function flushSession(payload) {
  await db.pending.put({ id: payload.id, status: 'sending', ... });
  const res = await fetch(API, { method: 'POST', body: ... });

  if (res.ok) {                        // 'done' 을 남기지 않고 바로 지운다
    await db.pending.delete(payload.id);
    await db.archive.update(payload.id, { sent: true });
    return;
  }
  // 4xx 는 몇 번을 보내도 같은 답이다 — 재시도를 멈춘다(429 제외).
  // 안 멈추면 확장 큐와 서버 ingest_failures 가 동시에 무한 증식한다.
  if (res.status >= 400 && res.status < 500 && res.status !== 429) { ... return; }
  // 실패 기록 — 다만 **이미 지워진 레코드를 되살리지 않는다**
}
  • 서버는 같은 session_id를 두 번 받아도 안전하다 — 클라이언트 UUID PK + ON CONFLICT DO NOTHING
  • onStartup에서 고아 세션 정리. 단 마지막 활동에서 30분이 안 지났으면 끊지 않고 이어간다 — 크롬 업데이트 직후 재시작에서 작업이 둘로 쪼개져 10분 필터에 버려지는 것을 막는다
  • 세션 종료 시각 ≠ 전송 시각. 서버는 received_at이 아니라 started_at으로 정렬한다
  • 마감 순서는 archive 먼저, draft 정리 나중, 전송 맨 마지막. archive 가 유일한 내구성 기록이라 draft 를 먼저 지우면 복구 경로가 없다
  • 흡수 순서는 저장 먼저, 삭제 나중. 최악이 "같은 이벤트를 한 번 더 흡수"(활동량이 살짝 부풀 뿐)이고, 반대 순서의 최악은 영구 유실이다

04

세션 판단 규칙

이 세션 하나가 LLM에게 “무슨 일을 했다” 한 문장으로 요약될 수 있는가.

규칙을 더 늘릴지 말지는 이 질문으로 결정한다.

종료 조건 네 가지

function shouldClose(s, now) {
  if (now - s.lastActivity > 30*60*1000)  return 'idle';
  if (contextSwitched(s, now))            return 'switch';
  if (now - s.startedAt > 4*60*60*1000)   return 'maxlen';
  if (dayBoundaryCrossed(s, now))         return 'day';
  return null;
}
조건이유
idle 30분기본 조건
maxlen 4시간상한이 없으면 8시간 코딩이 세션 하나가 되어 요약이 뭉개진다. continued_from을 남겨 서버가 이어붙인다
day 새벽 4시자정 기준이면 새벽 작업이 이틀로 쪼개진다

맥락 전환

function contextSwitched(s, now) {
  const recent = s.events.filter(e => now - e.at < 10*60*1000);
  if (recent.length === 0) return false;

  const newCat = dominantCategory(recent);
  if (newCat === s.primaryCategory) return false;

  const drift = now - firstEventOfCategory(recent, newCat).at;
  return drift >= 10*60*1000;
}

최근 10분이 계속 다른 카테고리면 전환. 10분 유예는 잠깐 이탈했다 돌아오는 것을 안 끊기 위함이다.

예외 A — 보조 도메인 흡수

const COMPANION = ['google.com', 'stackoverflow.com', 'chatgpt.com',
                   'claude.ai', 'developer.mozilla.org'];

검색·문서·AI 도구는 앞선 맥락에 흡수시켜 카테고리 판정에서 제외한다. 기획 #8의 GitHub + ChatGPT + Redis Docs → "Redis 캐싱 구현" 예시가 이 규칙 덕에 성립한다. 없으면 세 개로 쪼개진다.

예외 B — 왕복은 끊지 말고 태그

if (s.switchCount >= 3 && now - s.startedAt < 60*60*1000) {
  s.tag = 'scattered';
  return false;   // 끊지 않음
}

GitHub↔YouTube 왕복을 네 개로 쪼개는 대신 scattered 태그를 붙인다. LLM이 “집중이 잘 안 되는 날”로 요약할 수 있고, 성격 축(몰입형↔산만형)의 입력이 된다. 버그를 데이터로 바꾸는 지점.

알려진 왜곡 — 조건의 뒷항이 세션 시작 후 60분이라, 태그가 붙을 수 있는 창은 처음 60분뿐이다(태그는 한 번 붙으면 안 떨어진다). 실측에서 241분·이탈 8회 세션은 태그가 없고 47분·이탈 3회 세션은 붙었다. 즉 이 태그는 “여기저기 움직였다”가 아니라 “시작하자마자 왔다갔다했다”를 뜻한다. 세션을 안 끊는 판정으로는 맞지만, 그대로 성격 축의 감점으로 들어가는 것은 어긋나 있다.

예외 C — 백그라운드 재생

music.youtube.com, spotify.com은 활성 탭이 아니면 카테고리 판정에서 제외한다. 안 그러면 모든 코딩 세션이 음악 세션이 된다.

전송 필터

function isWorthSending(s) {
  if (s.durationMin < 10)   return false;
  if (s.activityScore < 50) return false;
  if (s.uniqueDomains === 1 && s.category === 'entertainment'
      && s.activityScore < 150) return false;
  return true;
}

세 번째는 영상 필터다. 다만 점수 150 이상은 통과시켜 진짜 강의 시청은 살린다.

실측(나흘) — 전송된 세션 26개, 하루 5~7개. 길이 47~241분.

길이는 "쓴 시간"이 아니라 "관측 창"이다 — duration_min 은 started_at → lastActivityAt 이라 중간의 자리비움이 그대로 들어간다. 자리비움이 30분을 넘으면 세션이 갈라지지만, 10~30분 자리비움은 세션을 안 끊고 길이만 늘린다. 그 값이 기억 점수의 '평소보다 긴 세션'(+20)과 성격의 몰입형 축에 직접 들어가서, 25분씩 자리를 비우는 사람이 붙어서 일한 사람보다 몰입형으로 찍힌다. 구간별 체류(sec)는 10분 상한으로 캡되는데 duration_min 만 캡이 없다.

압축 — 무엇을 모델에게 보이나

마감 시점에 buildCompressedLog 가 rawEvents 를 구간(segments)으로 접는다. 상한은 전부 개수다.

상한값하는 일
MAX_SEGMENTS20넘으면 최신 20구간만 상세로 남기고 앞부분은 earlier 합계로 접는다
FOLD_UNDER_SEC60초1분도 안 머문 곳은 칸을 안 주고 앞 구간의 via로 접는다
MAX_QUERIES15검색어. 반복 횟수와 구간을 함께 남긴다
제목·경로200자절단

세 가지가 실측으로 드러난 뒤 붙었다.

  • 구간 접기 — 18세션 321구간 중 72%가 1분 미만이었다. 상한 20칸이 경유지로 차서 241분 세션에서 모델이 본 게 마지막 7분뿐인 경우까지 나왔다. 그 상태의 outcome 판정은 세션이 아니라 끝자락에 대한 판정이다
  • 검색어 반복 횟수 — 프롬프트의 stuck 기준이 "같은 검색어가 반복되고"인데, 압축이 중복을 제거해 판정 근거를 판정 직전에 지우고 있었다. 여덟 번 물어도 한 번과 같은 입력이었고 실제로 stuck이 한 번도 안 나왔다
  • 구간별 체류 시간(sec) — start~end 는 첫 관측과 마지막 관측 사이라 관측이 하나면 0이다. 실측 세션에서 구간 span 합이 31분인데 세션 길이는 197분이었다

검증 방법

실제로 이렇게 했다 — 규칙만 돌려 세션 분할을 확인하고, 원본을 콜드 스토리지에서 다시 꺼내 새 압축기에 태워보는 스크립트(replay-raw.mts)를 만들었다. 저장된 compressed_log 로는 압축기 변경을 검증할 수 없다 — 그건 옛 압축기의 결과물이라 무엇이 달라졌는지 알 수 없기 때문이다.
05

서버 파이프라인

세션 ≠ 경험

세션은 관측 단위(규칙으로 자동 도출), 경험은 의미 단위(LLM 판단)다. 대부분 1:1이지만 정확히는 N:M이다.

  • 한 경험이 여러 세션에 걸침 — 점심 전후로 이어지는 작업. maxlen 절단은 정의상 경험 하나를 둘로 쪼갠다
  • 한 세션에 여러 경험 — 같은 카테고리 안에서 프로젝트가 바뀌는 경우
초판에서 변경 · 경험 분할 구현
초판N:M 이라고 적어두고 스키마는 session_id UNIQUE — 세션당 하나로 박혀 있었다
현재모델이 also 로 갈래를 내고 segment_ids 로 구간을 배정한다
실측하니 18세션 중 6건에 대상이 둘 이상이었고, 셋은 Project NA 와 Army Sim 이 한 세션에 있었다. 전부 Project NA 갈래로 흡수돼 Army Sim 은 경험 2건으로 과소 기록됐다. 세션 자체는 안 나눈다 — 그건 관측이고, 확장은 localhost 가 어느 프로젝트인지 판정할 수 없다(도메인이 아니라 제목에만 있다). 나누는 것은 해석 층의 일이다.

나누는 판단은 모델이, 시간과 문턱은 코드가 잰다. 모델에게 분 단위 합산을 시키면 틀리고, 틀린 채로 저장되면 되돌릴 수 없다. 배정이 어긋나면 나누지 않고 하나로 돌아간다(구간 겹침·범위 밖·시간 없음). 문턱 10분을 못 넘긴 갈래는 버리지 않고 주된 경험의 서술로 흡수된다.
저장 방식 결정
기각하루 동안 갱신하다 자정에 저장
결정세션 종료 시 즉시 저장, 요약은 계층으로 쌓음
자정 방식은 감정 실시간이 깨지고, 오늘 데이터를 못 보며, 결정적으로 늦게 도착하는 세션을 넣을 곳이 없다. 세션은 며칠 뒤에 도착할 수 있으므로 시간 기반 저장은 전송 모델과 구조적으로 맞지 않는다.
sessions      확장이 만듦, 규칙 기반      하루 5~7개 전송
   ↓
experiences   세션 종료 시 즉시 저장       세션당 1~3개  ← 원자 단위, 불변
   ↓
threads       같은 대상끼리 묶음         며칠~몇 주  (모두 갈래를 갖는다)
   ↓
memories      점수 넘은 것만               갈래당 하나에 근거가 쌓인다

갈래당 기억은 하나다(uq_memories_thread). 예전에는 조건을 넘길 때마다 따로 생겨서 같은 갈래에 기억이 셋씩 붙었고(실데이터: 경험 9건 → 기억 3개), 셋 다 누르면 같은 위성이 떴다. 지금은 이미 있으면 experience_ids 에 근거를 더하고 needs_resummary 만 세운다 — 다시 쓰는 것은 밤의 일이다.

Experience Engine

세션 종료 시 LLM 1회 호출. 기존 컨텍스트 주입이 필수다. 없으면 아래를 구분하지 못한다.

"TypeScript로 기능을 구현했다"     ← 늘 하던 것
"처음으로 TypeScript를 써봤다"     ← 신규 스킬 획득

프롬프트에 보유 스킬 목록·최근 경험 3건·진행 중 갈래·잠긴 갈래 후보·사람이 바로잡은 판정의 집계를 함께 넣는다. 최근 경험은 이 세션보다 앞선 것만 — 확장이 오프라인이었다가 사흘 뒤에 보내면 모델이 미래를 보고 판정하게 된다.

출력 제약 — 대사는 80자 · 슬롯당 하나씩 정확히 4개. 초과분은 문장 경계에서 자른다(한복판에서 끊으면 화면에 그대로 드러난다). 모델은 "80자 이내"라고 해도 105자를 낸다 — 길이를 지키게 하는 것보다 자르는 쪽을 고치는 게 확실하다.

검증이 폐기가 되면 안 된다 — 예전에는 대사 한 줄이 81자면 zod 가 출력 전체를 반려했고, 멀쩡한 summary·category·outcome·skills 까지 통째로 버려져 그 세션은 경험이 되지 못했다. 대사는 파이프라인에서 가장 안 중요한 값(슬롯당 1행씩 덮어써지는 캐시)인데 그게 가장 중요한 값을 죽였다. 지금은 자를 수 있는 것은 자르고, 개수도 강제하지 않는다.

프롬프트 버전

프롬프트를 고치면 번호를 올리고 llm_outputs.prompt_version 에 남긴다. "v3 에서 v4 로 바꿨더니 stuck 이 나오기 시작했다" 같은 비교가 가능해야 하기 때문이다. 현재 v9. 판정을 실제로 바꾼 것들:

버전바꾼 것왜
v3outcome 판정 기준 명시, is_first_time 완화값 네 개를 나열만 하고 언제 무엇을 고를지 안 적었더니 6건 중 5건이 explore 로 쏠렸다. 기준을 안 주면 모델은 가장 안전한 값으로 도망간다
v4사람 판단 우선순위교정이 들어오기 시작했는데 모델이 자기 추론으로 다시 덮으면 교정은 아무 데도 안 쓰이는 라벨 더미가 된다
v7구간별 체류·곁가지·앞부분 요약상한 20칸이 1분 미만 경유지로 차서 긴 세션의 앞부분이 통째로 잘렸다(241분 중 234분이 안 보인 경우)
v8「대상별 체류 합계」를 미리 계산해 준다시간이 세 군데(segments·via·earlier)에 흩어져 있어 "큰 대상이 둘이었나"를 알려면 모양이 다른 목록에 걸친 산수가 필요했다 — LLM 이 특히 못하는 일이다
v9구간마다 번호(i)를 박아서 준다프롬프트는 "구간 번호를 적으라" 했는데 번호가 없었다. 모델이 20칸 배열의 인덱스를 스스로 세다 한 칸씩 밀렸고, 그러면 그 구간들의 체류 합도 틀려 분할 문턱과 시간이 전부 어긋난다. A/B 로 3:0

Memory Engine

LLM 재호출 금지. 규칙 점수로 선별한다.

신규 스킬 등장                    +50
해당 스킬 첫 시도                  +40
막힘 → 성공 (직전 stuck, 이번 success)  +35
3일 이상 공백 후 복귀               +30

60점 이상 → 장기 기억

초판의 다섯 개로는 임계값을 넘을 길이 사실상 없었다. 신규 스킬과 첫 시도가 겹쳐야만 도달하는데 is_first_time 이 잘 안 뜨면 그 유일한 길마저 막힌다 — 하루 여섯 경험에 기억 0건이 실제로 나왔다. 문턱을 80에서 60으로 낮추고, 드물게 발동하면서 뜻이 분명한 신호 둘(막힘 돌파·휴면 스킬)을 더했다.

초판은 "기억의 입력은 experience 가 아니라 thread 의 상태 변화"라고 했다. 절반만 맞았다 — 완결(thread_complete)은 모델이 못 내는 값이었다. 역대 LLM 호출 75회 중 completed=true 가 한 번도 없었고, 프롬프트가 완결 예시로 못 박은 세션을 그대로 재현해도 false 였다. 브라우징 기록은 "무엇을 했나"를 말하는데 완결은 "더 할 게 없다"는 판단이라 안 한 일에 대한 진술이어서 기록에 흔적이 없다. 그래서 사람이 지도에서 직접 누른다.

대신 갈래에 경험이 6건 쌓이면 그 자체로 기억이 된다(deepened). 오래 붙들고 있는 일은 매 세션이 특별할 게 없는데도 남을 만하다 — 몇 달째 이어지는 갈래에 기억이 하나도 안 생기던 구멍을 메운다.

사람 판단 — declared

experiences·dialogues·daily_logs 가 전부 LLM 생성물(inferred)이라, 그것만으로는 1년 뒤 학습 데이터를 뽑아도 모델을 다시 학습시키는 꼴이 된다. 사람의 판단이 들어오는 통로를 따로 냈다.

테이블담는 것
corrections사람이 실제로 내린 판단. append-only — 마음을 바꾼 이력 자체가 신호다
questions캐릭터가 던진 질문과 그 결말. 침묵도 기록한다

둘로 나눈 이유: 하나로 합치면 human_value 가 NULL 인 행이 "안 물어봤다"인지 "묻고 답을 못 받았다"인지 구분되지 않는다. 무응답을 동의로 세면 데이터가 조용히 오염된다 — 무응답은 대개 동의가 아니라 안 본 것이다.

experiences 는 여전히 UPDATE 하지 않는다. 유효값은 저장된 값이 아니라 읽을 때 겹쳐서 만드는 값이다 — experiences(inferred) + corrections 최신 1건(declared).

주기

시점처리
세션 종료 시Experience Engine (LLM 1회) — 경험·갈래·기억·대사·스킬·레벨
야간 · KST 03:00일기 → 기억 재요약 → 갈래 정리 → 성격 → 레벨 캐시 → 질문 생성

순서에 뜻이 있다. 갈래 정리가 성격보다 앞이다 — 뒤에 두면 오늘 밤 무활동 임계를 넘긴 갈래들이 성격 계산이 끝난 뒤에야 abandoned 가 되어 완결형 축이 늘 하루 늦는다. 질문 생성이 마지막인 것은 앞 단계가 그날 경험을 다 반영한 뒤라야 후보가 온전하고, 실패해도 일기·성격·레벨에 영향이 없기 때문이다.

야간 LLM 호출은 둘 — 일기(유저당 1회)와 기억 재요약(근거가 늘어난 기억만). 성격·레벨·질문은 전부 규칙 기반이다.

성격은 세션 하나로 바뀌면 안 된다. 최소 2주 이동평균.

초판의 '몰두'(세션 길이 2배)는 뺐다. 그건 기억 점수의 항목이지 감정의 재료가 아니고, 대신 기본값이 필요했다 — 아무 규칙에도 안 걸리는 날이 대부분인데 그때 표시할 것이 없었다.

교정이 감정까지 닿아야 한다 — /diary 에서 "이건 막힌 게 아니라 해낸 거야"라고 세 건을 고쳤는데 홈의 캐릭터가 계속 답답해하면(원본 outcome 을 보므로) 아무도 안 누르고, 그러면 declared 가 쌓이지 않는다. 감정 계산도 교정을 겹친 값으로 한다.

레벨 AND 데이터 조건

레벨만으로 게이팅하면 깨진다. 하루 12시간씩 몰아친 사용자가 30일 만에 Lv.30이 되면 searchMemory()가 켜지는데 연결할 과거가 없다.

LLM은 툴이 있으면 부르고, 결과가 빈약해도 지어낸다. 조건 미달이면 툴을 아예 빼야 한다. “데이터 부족” 응답을 돌려주면 그 상태로도 말하려 든다.
function buildTools(level, stats) {
  const tools = [];
  if (level >= 5  && stats.experienceCount >= 5)   tools.push(getTodayExperiences);
  if (level >= 10 && stats.activeDays >= 14)       tools.push(getWeeklyPattern);
  if (level >= 30 && stats.memoryCount >= 20
                  && stats.oldestMemoryDays >= 60) tools.push(searchMemory);
  return tools;
}

08

인증

익명으로 시작한다

확장 설치 시 익명 키를 발급받고 그것만으로 식별한다. 회원가입 화면도 비밀번호도 없다.

chrome.runtime.onInstalled.addListener(async () => {
  const { key } = await fetch(API + '/register', { method: 'POST' })
                        .then(r => r.json());
  await chrome.storage.local.set({ extensionKey: key });
});

온보딩 마찰이 0이고, “AI가 태어났다”는 연출과도 맞는다. 가입 폼부터 뜨면 그 감각이 깨진다. Day 0에 사용자가 하는 행동은 이름 입력 하나뿐이어야 한다.

그대로 두면 DB를 둔 이유가 사라진다

키가 확장 스토리지에만 있으면 재설치·PC 교체·프로필 초기화에서 전부 유실된다. 서버에 데이터가 살아있어도 찾아올 방법이 없다. “캐릭터 유실 방지”가 DB 도입의 근거였는데 그게 무효화된다.

이 문장이 2026-08-08 에 그대로 실현됐다. 확장을 삭제 후 재설치하면서 IndexedDB 와 chrome.storage.local 이 함께 사라졌고(같은 오리진이다), registerExtensionKey 의 "이미 키가 있으면 재발급하지 않는다" 가드가 무력해져 새 익명 키가 발급됐다. 그 순간부터 세션이 새 계정에 쌓였다.

발견이 늦은 이유가 더 나쁘다 — 사이트 쿠키는 옛 키를 가리켜 화면에 아무 표시도 안 났다. "8/8 경험이 왜 하나뿐이지"로 며칠 뒤에 드러났다. 유저 둘을 다시 합치고, 세션을 이관해 재처리했다.

그래서 붙인 것

  • 미러 폴백 — chrome.storage.local 에 써두던 사본을 이제 실제로 읽는다. 예전에는 쓰기만 하고 읽는 코드가 없었다. 다만 이번 사고(스토리지 전체 소실)는 이걸로 못 막는다. Dexie 만 깨지는 경우를 막는다
  • 발급 경고 — 새 키를 발급하면 툴바에 배지를 세우고 팝업 맨 위에 배너를 띄운다. [기존 캐릭터에 연결] / [처음 설치예요]. 확인할 때까지 안 사라진다

확장은 첫 설치와 "스토리지를 잃은 재설치"를 구분할 수 없다 — onInstalled 의 reason 이 둘 다 'install' 이다. 그래서 발급 자체는 막지 않고(온보딩에 마찰을 주면 첫 사용자가 손해다) 조용히 갈리지 않게만 한다. 판단은 사람이 한다.

사이트를 본체로 삼기로 했으므로 사이트가 사용자를 알아볼 방법도 필요하다.

지금 사이트는 쿠키로 알아본다

OAuth 가 붙기 전까지의 다리다. 확장 키를 /connect 에서 한 번 받아 httpOnly 쿠키(400일)로 심고, 서버 컴포넌트는 그 쿠키로 users 를 조회한다. 확장이 그 페이지에 content script 를 주입해 키를 넘기므로 사용자는 아무것도 입력하지 않는다.

  • localStorage 에 키를 두지 않는다 — XSS 방어. 키가 곧 자격증명 전체다(비밀번호가 없다)
  • /api/connect 는 Origin 검사를 한다. 쿠키를 심는 것은 로그인이고, 검사가 없으면 로그인 CSRF 가 성립한다 — 공격자가 자기 키를 피해자 브라우저에 심으면 이후 피해자의 활동이 공격자 계정에 쌓인다
  • 오류 로그에 err 를 통째로 찍지 않는다 — 드리즐 오류 메시지에 바인딩 파라미터(=키 원문)가 들어 있다

계정 연결을 레벨 언락처럼 다룬다 미구현

Day 0    설치 → 익명 키 발급 → 바로 시작
         AI: "..."  → 이름 지어주기

Lv.5쯤   AI: "나 이제 하루를 기억할 수 있어.
              근데 이 브라우저를 벗어나면 다 잊어버려."
         [ 계정 연결하기 ]

첫날 가입 폼을 들이밀면 이탈하지만, 사흘 키운 캐릭터를 잃기 싫어지는 시점에는 사용자가 자발적으로 누른다. 이 요청이 캐릭터의 대사로 나오면 UI가 아니라 서사가 된다.

인증은 구글 OAuth 하나만. 비밀번호 관리·재설정 메일·해싱이 전부 사라지고, 크롬 사용자면 클릭 한 번이다.

기기 분리 미구현

기기가 여러 대면 키도 여러 개다. 개발자가 주 사용자라면 노트북과 데스크톱 두 대는 기본이므로 실질적으로 필요하다.

CREATE TABLE devices (
  extension_key  TEXT PRIMARY KEY,
  user_id        UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  label          TEXT,              -- '회사 노트북'
  last_seen_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

이러면 두 기기의 세션이 같은 캐릭터로 합쳐진다.

초판의 지시를 안 지켰다
초판users 는 지금부터 google_id·email·linked_at 을 갖고 있어야 나중에 마이그레이션이 없다
현재users = id · extension_key · created_at 셋뿐. devices 테이블 없음
키 하나가 곧 유저 하나라, 지금 구조로는 기기 둘을 합칠 방법이 없다. 08-08 사고에서 유저가 갈렸을 때도 합치는 경로가 없어 세션을 손으로 이관하고 파생 데이터를 재구축해야 했다 — devices 가 있었으면 키를 한 유저에 더 붙이는 것으로 끝났다. 초판이 정확히 이 상황을 예상하고 미리 만들어두라고 했는데 안 했다.

홈 — 천체는 한 종류다

갈래 하나가 별 하나. 기억은 그 별의 광도이고 색온도다.

처음엔 둘이었다 — 기억이 별이고 갈래가 도는 것이었다. 그런데 갈래당 기억이 하나라 같은 것이 화면에 두 번 뜨고, 방향 문법이 두 벌이었다(기억은 trigger, 갈래는 분야). 한 계에 어휘가 둘이면 어느 것도 못 읽는다. 합치면 기억은 사라지는 게 아니라 별의 성질이 된다.

v2 — 새 탭 교체 (보류)

보류하되 폐기하지 않는다. 사이트를 먼저 만들면 API가 이미 있어 붙이기 쉽다.

  • 레벨·이름은 우측 상단 구석 — 하루 40번 보는 화면이라 중앙에 크게 두면 사흘이면 질린다
  • 캐릭터와 대사가 정중앙, 대사만 세리프체 — 말하는 존재만 서체가 다르면 “UI가 아니라 누구”가 된다
  • 검색창 필수 유지, 단 대사 아래 배치
  • chrome.topSites로 자주 가는 사이트 복원 — 없으면 “원래 있던 게 사라졌다”고 느낀다
document.querySelector('input').focus();            // 최우선
chrome.storage.local.get('dialogue').then(render);  // 그 다음

Ctrl+T 직후 타이핑하는 사용자가 첫 글자를 놓치면 안 된다.

비용 5배 차이보다 심각한 문제가 둘 있다. 대사가 매번 바뀌면 같은 하루인데 말이 달라져 기억이 있는 존재로 느껴지지 않는다. 그리고 1~3초 로딩 스피너가 보이는 순간 사용자가 이탈한다.

세션 종료 시 시간대별 대사 4개(morning·afternoon·evening·night)를 미리 만들어둔다. PK 가 (user_id, slot) 이라 유저당 정확히 4행이고, 홈은 현재 슬롯 1행만 읽는다. 경험 판정과 같은 LLM 호출 하나에 들어 있어 대사만 따로 부르지 않는다.

네 슬롯이 전부 같은 세션을 말한다 — 아침에 열어도 그 대사는 어젯밤 세션에서 나온 것이다. 시간대별 어감을 미리 준비해두고 꺼내 쓰는 방식이라 내용은 최신 세션 하나에 매인다. 의도한 트레이드오프다.

experiences는 절대 UPDATE 하지 않는다.

나머지는 전부 여기서 재계산 가능한 파생 테이블로 둔다. 그러면 나중에 규칙이나 프롬프트를 바꿔도 되돌릴 수 있다. thread_id 부착 1회만 예외다.

왜 실패와 원본을 따로 남기나

ingest_failures 는 "실패"만 남긴다. 그래서 성공한 판정의 근거가 어디에도 없었다 — outcome 이 왜 explore 였는지 나중에 물으면 세션을 다시 LLM 에 태우는 것 말고 답할 방법이 없었고, 그마저 비교 대상인 이전 출력은 이미 experiences 로 가공된 뒤였다. llm_outputs 에 tool_use.input 을 가공 전 그대로 넣고 모델·프롬프트 버전을 함께 남긴다.

assertion class — 무엇을 믿을 것인가

declared  사람이 직접 말한 것      corrections · questions · thread 완결
observed  센서가 본 것            sessions · Storage 원본
inferred  모델이 추론한 것        experiences · dialogues · daily_logs · memories

이 위계가 프롬프트에도 들어간다. 충돌하면 declared > observed > inferred 순으로 믿는다. 이걸 안 적으면 모델이 사람이 고쳐놓은 값을 자기 추론으로 다시 덮는다.

설명이 필요한 결정

sessions.id를 클라이언트가 만든다. 서버 생성 UUID면 재시도 시 같은 세션이 두 번 들어간다. 클라이언트 UUID를 PK로 두면 ON CONFLICT DO NOTHING 한 줄로 멱등성이 끝난다.

emotion 컬럼 대신 experiences.outcome. success / partial / stuck / explore 네 개가 감정의 재료다. stuck 3연속이면 답답, success면 성취. 감정 자체는 조회 시점에 계산한다.

memories.forgotten_at은 삭제가 아니라 마킹. Lv.80 망각이 켜져도 데이터는 남고 검색 결과에서만 빠진다. 성능 최적화가 서사와 일치하는 드문 지점이다.

daily_logs.prompt_version이 숨은 핵심. 일기 프롬프트를 개선하면 과거 일기를 전부 재생성할 수 있다. experiences를 불변으로 둔 덕분에 가능하다.

자리증상
재생 틱과 유휴 시계보이는 탭의 영상 재생이 lastActivityAt 을 밀어올린다. 듀얼 모니터에 영상을 띄워두고 자리를 뜨면 idle 이 영영 안 걸리고 maxlen 4시간까지 간다 — 그 세션은 활동 점수가 높아 필터를 다 통과한다. 반대로 순수 시청 10분은 점수 30점이라 걸러진다
레벨 계산 인자엔진은 경과 시간을 24로 나누고 배치는 날 경계를 센다. 공식은 공유하는데 입력이 달라 밤에 오른 레벨이 다음 세션에 내려갈 수 있다
성격 스냅샷 중복 방지비교 기준이 실행 시각이라 조건이 절대 성립하지 않는다 — 하루에 두 번 돌리면 점이 둘 찍힌다
corrections·questions RLS다른 테이블은 전부 켰는데 이 둘만 빠졌다. 이 시스템에서 유일하게 다시 만들 수 없는 데이터다
dialogues 역행user_skills·threads 는 GREATEST 로 시각 역행을 막는데 여기만 무조건 덮는다. 오프라인 사흘치를 몰아 보내면 가장 오래된 세션의 대사가 남을 수 있다

리스크

스토어 심사. 방문 기록 전체를 외부 전송하는 확장은 Chrome Web Store Limited Use 정책 대상이다. <all_urls> 권한과 겹쳐 심사 난이도가 높다. 공개 배포 시 개인정보처리방침 필수.

품질 리스크(프라이버시와 별개). 은행·의료·DM·비밀번호 입력창의 이벤트는 경험으로 쓸모가 없으면서 LLM 토큰만 소모한다. 최소 도메인 blocklist는 비용 절감 장치로 권장한다.

초반 이탈. Lv.1은 말도 못 하고 보여줄 것도 없다. 레벨 커브를 앞으로 당겨 Lv.5를 사흘 안에 도달시키는 것으로 대응한다.

LLM 환각. 데이터가 빈약해도 그럴듯하게 지어낸다. 툴 게이팅과 출력 스키마 검증으로 대응한다.

다음 단계

초판의 여섯 항목은 전부 끝났다. 지금 남은 것은 순서대로다.

  1. RLS 두 줄 — corrections·questions. 보안이고 한 줄씩이다
  2. 재생 틱이 유휴 시계를 리셋하지 않게 — 유령 4시간 세션을 막는다. 카테고리 투표와 활동 점수에는 그대로 남겨야 순수 시청 세션이 안 죽는다
  3. 레벨 인자 통일 · 성격 스냅샷 중복 방지 · dialogues 역행 — 각각 한 줄
  4. 실제로 쓴 시간(attended_min) — duration_min 은 관측 창이라 자리비움이 들어간다. 기억 점수와 몰입형 축만 새 값을 보게 한다
  5. 교정 전파 — 성격·일기·질문 순위가 교정을 겹친 값을 보게. 설계 결정이 필요하다
  6. 망각 구현 — 읽는 쪽은 다 있고 forgotten_at 을 세우는 곳만 없다
  7. 계정 연결(OAuth) · devices — 08-08 사고가 이유다. 키 하나가 유저 하나인 한 기기를 못 합친다

운영하며 배운 것

모델에게 세게 하지 마라. 숫자를 세게 하면 틀린다.

구간 번호를 안 주고 "몇 번째인지 적어라" 했더니 한 칸씩 밀렸고, 흩어진 시간을 더하라고 했더니 큰 대상을 놓쳤다. 둘 다 미리 계산해서 주니 해결됐다. 판정은 맡기고 산수는 코드가 한다.

기준을 안 주면 모델은 가장 안전한 값으로 도망간다.

explore 로 쏠린 것도, is_first_time 이 안 뜬 것도, completed 가 한 번도 안 나온 것도 같은 실패였다. 값을 나열만 하고 언제 무엇을 고를지 안 적었다.

자를 수 있는 것을 폐기 사유로 삼지 마라.

대사 한 줄이 81자라고 경험 전체를 버리던 자리가 있었다. 가장 안 중요한 값이 가장 중요한 값을 죽이면 안 된다.

조용히 틀리는 것보다 드러나는 편이 낫다.

also 가 잘려도 검증을 통과해 경험이 소리 없이 하나로 줄던 자리, 계정이 갈렸는데 화면에 아무 표시도 안 나던 자리 — 둘 다 며칠 뒤에야 발견됐다. 실패는 크게 실패해야 한다.
