01

한눈에 보기

브라우저에서 무엇을 했는지 관찰해서, 하루에 몇 문장으로 압축하고, 그중 남을 만한 것을 기억으로 남긴다. 캐릭터는 그 기억을 먹고 자란다.

로그를 저장하지 않는다. 의미 있는 경험을 저장한다.

다섯 층

위로 갈수록 양이 많고 아래로 갈수록 뜻이 진하다. 층마다 만드는 주체가 다르다 — 규칙으로 될 일에 LLM을 쓰지 않고, 판단이 필요한 곳에만 쓴다.

전부 Haiku다. 기억 생성·성격·레벨·질문은 전부 규칙 기반이라 호출이 없다.

LLM은 말을 만드는 엔진이고, 진짜 AI는 Memory Engine이다.

관측 — 무엇을 보나

이벤트 세 종류

kind출처언제점수
activitycontent script10초 틱 — 입력이나 재생이 있을 때만입력량에 비례
tab_activatedchrome.tabs.onActivated탭 전환5
tab_updatedchrome.tabs.onUpdated로드 완료0

content script는 그 페이지 안만 본다. 탭을 옮기거나 새 URL이 열리는 건 페이지 밖의 사건이라 chrome.tabs로만 잡힌다. 반대로 스크롤·클릭·키는 서비스 워커가 못 본다. 그래서 둘 다 있다.

활동 점수

eventScore = scrolls×1 + clicks×2 + keys×1
           + (탭전환 ? 5 : 0) + (재생중 ? 0.5 : 0)
tab_updated가 0점인 것이 두 가지를 가른다.

① 유휴 시계를 안 민다. 예전엔 이것도 밀어올려서, 배경 탭이 자동 새로고침될 때마다 유휴 시계가 0으로 돌아갔다. idle이 도달 불가능한 조건이 됐고 실측으로 세션 8건의 종료 사유가 switch 7 / maxlen 1, idle 0건이었다. 자리를 뜨면 idle로 닫히는 게 정상인데도.

② 시간을 안 먹는다. 열어둔 네이버 메일이 로드를 끝낼 때마다 최대 10분씩 가져가던 게 사라졌다 — 그 시간엔 다른 탭에서 일하고 있는데 "가장 오래 머문 곳"이 그 배경 탭으로 찍히면 세션 전체의 분야 판정이 틀어진다.

다만 방문 사실 자체는 남긴다 — 도메인 맵에 키는 만들고 값만 0이다. 지우면 unique_domains의 뜻이 "방문한 도메인 수"에서 "주의를 준 도메인 수"로 바뀌어 단일 도메인 영상 필터가 훨씬 잘 걸린다.

원본(Storage)에도 건다. 원본은 무손실이 목적이라 압축은 안 걸지만, 리댁션은 다르다 — 한 번 새면 회수 경로가 없다.

분야 판정 — 세 겹

도메인 사전 335개가 1차로 찍는다(서브도메인은 longest-suffix 매칭 — music.youtube.com이 youtube.com보다 먼저 걸린다). 다만 이건 참고값이고 최종 분야는 나중에 모델이 내용으로 다시 판정한다.

예외대상처리
A 보조 도메인google, stackoverflow, chatgpt, claude, MDN, 번역기 …카테고리 투표에서 항상 제외
B 왕복이탈 3회 + 세션 시작 60분 이내안 끊고 scattered 태그만
C 배경 음악music.youtube, spotify, apple music, soundcloud활성 탭이 아닐 때만 제외
경유지newtab, etc투표에서 제외

예외 A가 없으면 GitHub + ChatGPT + Redis Docs가 세 세션으로 쪼개진다. 예외 C가 없으면 모든 코딩 세션이 음악 세션이 된다.

투표는 개수가 아니라 활동 점수 가중이다. 재생 틱은 10초마다 꼬박꼬박 오기 때문에 개수로 세면 듀얼 모니터에서 보이기만 하는 유튜브가 실제 작업 분야를 뺏는다. 점수 기준이면 입력이 있는 작업이 압도하고, 순수 시청 세션은 경쟁자가 없어 여전히 시청으로 잡힌다.

실측 — 경유지 제외 규칙이 없을 때 16세션 중 9건에서 새 탭·빈 도메인이 우세 분야를 가져갔다. 한 세션에서는 ChatGPT로 25분을 보내는 동안 그 사이에 뜬 새 탭 두 개가 "25분간 etc에 머물렀다"로 읽혀 가짜 전환을 만들었다.

04

세션 — 언제 끊나

이 세션 하나가 "무슨 일을 했다" 한 문장으로 요약될 수 있는가.

종료 조건 넷 — 위에서부터

사유조건모델에게 어떻게 전해지나
idle마지막 활동 후 30분"하던 것을 놓고 자리를 떴다"
switch다른 분야가 10분 이상 우세"다른 분야로 넘어갔다"
maxlen세션 시작 후 4시간"잘렸다 — 끝나서 끝난 게 아니다"
dayKST 새벽 4시 경계"잘린 것이지 끝난 게 아니다"
shutdown브라우저 재시작 감지"브라우저를 껐다"

종료 사유는 outcome 판정의 직접 근거다. maxlen은 특히 중요하다 — 4시간에 잘렸다는 것은 하던 일이 끝나지 않았다는 뜻이라 success의 반증이다.

세션의 끝은 "닫힌 시각"이 아니다

endedAt      = min(lastActivityAt, now)
duration_min = round((endedAt - startedAt) / 60000)
왜 now가 아닌가 — idle은 마지막 활동 후 30분을 기다렸다 발동한다. now를 쓰면 그 30분이 통째로 세션 길이에 들어가서, 5분짜리 세션이 35분으로 계산돼 10분 전송 필터가 무력화된다. shutdown은 더 심하다 — 브라우저를 꺼둔 몇 시간이 다 들어간다.

자리를 비웠을 때

공백 길이에 따라 셋으로 갈린다. 경계가 두 개(10분·30분)다.

공백세션duration_min체류 합(sec)
< 10분안 끊김공백 포함공백 포함 — 둘이 같다
10~30분안 끊김공백 전부 포함10분까지만 (캡)
> 30분갈라짐각 조각만각 조각만

10분 미만 공백을 체류로 세는 것은 "생각하는 시간·읽는 시간"으로 보는 근사이고 대체로 맞다. 문제는 가운데 줄이다 — 16장 참고.

알람이 안 돈 구간은 따로 잡는다 — 노트북 절전이나 워커가 오래 안 깨어난 경우, 깨어나자마자 들어온 이벤트가 lastActivityAt을 갱신해버려서 now 기준 판정으로는 공백이 안 보인다. 그러면 밤 10시와 아침 9시가 한 세션이 되고 idle이 아니라 maxlen으로 잘려 11시간짜리 가짜 세션이 만들어진다. 그래서 흡수하기 전에 이벤트 시각으로 공백을 먼저 본다.

전송 필터

duration_min < 10                                    → too_short
activity_score < 50                                  → low_activity
unique_domains == 1 && 분야 == entertainment
                    && activity_score < 150         → single_domain_entertainment

세 번째는 영상 필터다. 150 이상은 통과시켜 진짜 강의 시청은 살린다(재생 틱 0.5점 × 6/분 → 50분 시청이 150점).

필터에 걸린 세션도 압축은 다 한다. compressed_log는 필터가 아예 안 보고, 버려질 세션도 archive에 탈락 사유와 함께 3일 남는다 — 필터 튜닝의 근거로 쓰라는 의도다.

05

압축 — 모델에게 뭘 주나

마감 시점에 buildCompressedLog가 한 번 돈다. 중간 압축 단계는 없다.

세 단계

① 도메인이 바뀔 때마다 구간(segment)으로 자른다
   raw 이벤트 수백 건 → 구간 수십 개

② 체류 시간을 잰다 (assignDwell)
   점수가 붙는 이벤트만, 다음 활동까지의 간격을 최대 10분까지

③ 접는다 (foldWaypoints)
   1분 미만 구간 → 앞 구간의 via 로. 시간은 앞 구간에 더한다
   양옆이 같은 도메인 + 같은 제목이면 잇는다

④ 넘치면 앞부분을 합계로 (earlier)
   최신 20구간만 상세로, 나머지는 "무엇을 몇 초" 로

왜 이렇게 됐나 — 셋 다 실측이 시켰다

① 구간 접기 — 18세션 321구간 중 72%가 1분 미만이었다. 상한 20칸이 경유지로 차서 241분 세션에서 모델이 본 게 마지막 7분뿐인 경우까지 나왔다. 그 상태의 판정은 세션이 아니라 끝자락에 대한 판정이다. 접어도 정보는 안 잃는다 — 도메인과 제목은 via에 남고, 잃는 건 1분도 안 머문 곳의 개별 시각뿐이라 판정에 쓸모가 없다.

② 검색어 반복 횟수 — 프롬프트의 stuck 기준이 "같은 검색어가 반복되고"인데, 압축이 중복을 제거해 판정 근거를 판정 직전에 지우고 있었다. 여덟 번 물어도 한 번과 같은 입력이었고, 실제로 stuck이 한 번도 안 나왔다. 지금은 {q, n, first, last}로 남긴다 — "n=8, 14:02~14:41" 이면 40분간 여덟 번 같은 걸 물었다는 뜻이다.

③ 구간별 체류 시간 — start~end는 그 구간의 첫 관측과 마지막 관측 사이라, 관측이 하나뿐이면 0이 된다. 2분을 머물러도 0분으로 보인다. 실측 세션에서 구간 span 합이 31분인데 세션 길이는 197분이었다.

같은 제목일 때만 잇는다

경유를 접고 나면 양옆이 같은 곳인 경우가 흔하다(작업 → 잠깐 검색 → 다시 작업). 둘로 남기면 "떠났다 돌아온 것"처럼 읽히므로 잇는다. 단 제목이 같을 때만 — 같은 localhost라도 제목이 Project NA와 SOLDIER : A DAY면 다른 일이고, 그걸 이으면 경험을 대상별로 나누는 근거가 압축 단계에서 먼저 뭉개진다.

마지막 구간은 길이와 무관하게 남긴다

마지막 이벤트에는 "다음 활동까지의 간격"이 없어 체류가 구조적으로 0이다. 그런데 그 구간이 곧 "무엇을 하다 끝났나"라서 outcome 판정이 가장 크게 기대는 자리다.

06

전송과 복구

서비스 워커는 30초 놀면 죽는다. 메모리에 아무것도 남기지 마라.

이 원칙 하나에서 나머지가 전부 파생된다. setInterval 금지(→ chrome.alarms), 전역 변수 버퍼 금지(→ IndexedDB), 응답 대기 중 상태 유지 금지(→ pending 레코드).

알람은 둘뿐

알람주기하는 일
sessionCheck1분흡수 → 종료 판정 → 마감
retry10분실패분 재전송 · 원본 업로드 · 보관 기한 정리

계획서에 있던 compress(5분)와 diary(1일)는 없앴다. 전자는 실제로 줄이는 게 없었고, 후자는 일기가 서버 야간 배치로 옮겨갔다.

알람이 사라지는 경로가 있다 — 확장 비활성화 후 재활성화처럼 onInstalled도 onStartup도 발화하지 않는 경우다. 그러면 rawEvents만 무한히 쌓이고 세션은 영영 마감되지 않는데 화면상 아무 증상이 없다. 그래서 워커가 깨어날 때마다 알람 존재를 확인하고 없으면 다시 등록한다.

마감 순서 — archive 먼저

① archiveClosed()      로컬 사본 + 탈락 사유 판정
② saveCurrentSession() draft 정리 (maxlen 이면 이어받기)
③ absorbRawEvents()    rawEvents → rawArchive 이동
④ flushSession()       전송 (기다리지 않는다)
archive가 유일한 내구성 기록이다. draft를 먼저 지우고 archive에서 죽으면(용량 초과 등) 그 세션은 archive에도 pending에도 없고 draft와 rawEvents까지 사라져 복구 경로가 하나도 없다. maxlen이면 더 나쁘다 — 이어받은 draft의 continued_from이 존재하지 않는 세션을 가리킨다.

흡수는 반대로 저장 먼저, 삭제 나중이다. 최악이 "같은 이벤트를 한 번 더 흡수"(활동량이 살짝 부풀 뿐)이고, 반대 순서의 최악은 영구 유실이다. 유실과 중복 중 중복을 택한다.

pending — 보내기 전에 넣는다

flushSession(payload):
  ① pending.put({ status: 'sending' })   ← fetch 전에 먼저
  ② fetch
     ├ 성공(2xx)        → pending.delete + archive.sent = true
     ├ 4xx (429 제외)   → pending.delete + 재시도 포기
     └ 네트워크 오류     → pending.put({ status: 'failed' })
                          단 이미 지워졌으면 되살리지 않는다
왜 먼저 넣나 — 응답을 기다리다 워커가 죽을 수 있다. 실패한 뒤에 넣는 구조라면 그때 pending에 아무 기록도 안 남고 세션이 영영 사라진다. 'sending' 행을 미리 박아두면 retry가 5분 넘은 것을 고아로 보고 다시 보낸다.

왜 4xx에서 포기하나 — 페이로드가 문제면 몇 번을 보내도 같은 답인데, 서버는 받을 때마다 ingest_failures에 행을 쌓는다. 확장 큐와 서버 테이블이 동시에 무한 증식하던 경로다. 429만은 시간이 풀어주므로 남긴다.

왜 부활을 막나 — 같은 세션에 flushSession이 둘 겹칠 수 있다(retry가 고아로 보고 재전송하는데 원래 fetch가 아직 살아 있을 때). 늦게 끝난 쪽이 무조건 쓰면 먼저 성공해서 지운 레코드가 'failed'로 부활해 10분마다 다시 전송된다.

오프라인일 때

무엇어떻게 되나
관측·세션화전부 로컬이라 정상 동작. 세션도 정상 마감된다
세션 전송pending에 failed로 쌓인다. 보관 기한 없음 — 며칠이 지나도 안 잃는다
원본 업로드rawArchive에 uploaded=0. 3일 지나면 버린다
재연결감지하지 않는다 — 다음 retry 틱까지 최대 10분

즉 오프라인이 3일을 넘기면 세션은 살고 원본만 잃는다. 원본은 없어도 되는 데이터이지 거짓으로 표시할 데이터가 아니라서, 실패해도 uploaded를 1로 올리지 않고 기한에 정리되게 둔다.

규칙이 먼저고 모델이 보탠다 — is_first_time

그 결과 이 컬럼에 매달린 것들이 전부 죽어 있었다. 기억 점수 +40이 안 붙고, 감정 '흥분'이 발동하지 않고, 성격의 개척형↔숙련형 축이 늘 숙련형 극단에 고정된다(사흘에 스킬 8개가 는 사용자가 "숙련형"으로 찍혔다).

지금은 hasNewSkill || 모델 판정이다. 확실히 아는 부분은 규칙이 채우고, 모델은 규칙이 못 보는 것(주제·방식·환경)만 보탠다.

나오는 것 — 코드가 다섯 번 손댄다

모델은 무엇이 있었나를 말하고, 코드는 그것을 어떻게 셀 것인가를 정한다.

모델 출력이 그대로 저장되지 않는다. 성격이 다른 다섯 종류의 손질이 순서대로 걸린다.

종류하는 일대상
①검증형태가 틀리면 폐기zod 스키마 · stop_reason
②자르기길면 줄여서 통과대사 80자 · 갈래 제목 100자
③방어환각을 강등존재하지 않는 갈래 id
④보강규칙이 덮어씀is_first_time · 스킬 domain
⑤회계시간을 다시 잼분할 여부 · duration_min · occurred_at

① 검증 — 폐기

tool_use 블록이 없다              → ingest_failures, 재처리 대상
stop_reason === 'max_tokens'      → 검증을 통과했어도 폐기
zod safeParse 실패                → ingest_failures

셋 다 processed_at 이 NULL 로 남아 재처리 대상이 된다

max_tokens를 폐기로 다루는 것이 핵심이다. also는 출력 끝에 오는데 스키마상 optional 이라 잘려도 검증을 통과한다 — 경험이 조용히 하나로 줄어든다. 필수 필드는 앞에서 이미 채워졌으니 겉보기엔 멀쩡한 판정이다.

② 자르기 — 폐기하지 않는다

대사 81자      clampSentence(text, 80)     문장 경계에서
갈래 제목      clampSentence(title, 100)
요약·기억 제목  자르지 않는다                 ← 상세에서 되살릴 방법이 없다
여기서 크게 데었다 — 예전에는 대사가 .max(80) 이라 81자면 zod 가 출력 전체를 반려했다. 멀쩡한 summary·category·outcome·skills 까지 통째로 버려져 그 세션은 경험이 되지 못했다. 대사는 파이프라인에서 가장 안 중요한 값(슬롯당 1행씩 덮어써지는 캐시)인데 그게 가장 중요한 값을 죽였다.

자를 수 있는 것을 폐기 사유로 삼지 않는다. 개수도 강제하지 않는다 — 대사가 3개만 와도 부족한 슬롯은 이전 것으로 버틴다.

③ 방어 — 환각 강등

thread.action === 'attach' 인데
  existing_thread_id 가 이번에 보낸 목록에 없다
      → action = 'new' 로 강등, 새 갈래를 만든다

스키마가 existing_thread_id를 z.uuid()로 조이지 않는 것도 이 때문이다. 모델이 "thread-1" 같은 걸 내면 스키마 단계에서 실패해 경험 전체가 폐기되어, 강등 경로에 도달조차 못 한다. 형태만 보고(string().max(64)) 존재 여부는 코드가 목록과 대조한다.

④ 보강 — 규칙이 먼저고 모델이 보탠다

isFirstTime = hasNewSkill || 모델판정
              ↑ user_skills 에 없던 이름이 있는가 (코드가 확정)

skill.domain = 모델판정 ?? CATEGORY_DOMAIN[category]
                            ↑ 모델이 빠뜨렸을 때의 대비책
프롬프트가 is_first_time 을 "보유 스킬 목록에 없던 것을 다뤘는가"로 정의했는데, 그건 추론이 아니라 비교 연산이다. 그런데 모델에게 물으니 실측 5/5 로 어긋났고 — 보유 목록이 텅 빈 첫 경험에서도 false 를 냈다. 규칙대로면 무조건 true 여야 하는 자리다.

그 결과 이 컬럼에 매달린 것들이 전부 죽어 있었다: 기억 점수 +40 이 안 붙고, 감정 '흥분'이 발동하지 않고, 성격의 개척형↔숙련형 축이 늘 숙련형 극단에 고정된다(사흘에 스킬 8개가 는 사용자가 "숙련형"으로 찍혔다).

프롬프트를 또 고치는 건 이미 한 번 실패한 방법이라, 확실히 아는 부분은 규칙이 채우고 모델은 규칙이 못 보는 것(주제·방식·환경)만 보탠다.

⑤ 회계 — 다음 절 전체

분할 여부·시간 계산이 여기 속한다. 가장 크고 판단이 많은 자리라 따로 다룬다.

한 세션을 여럿으로 나누기 — 누가 무엇을 정하나

의미는 모델이, 회계는 코드가.

이 층에서 가장 헷갈리는 것이 "누가 나누는가"다. 답은 둘 다이고, 묻는 질문이 서로 다르다.

단계묻는 것보는 것결과
① 모델이게 다른 일인가압축 로그 — 도메인·제목·검색어·시간also 에 갈래 + segment_ids
② 코드이걸 따로 셀 만한가그 구간들의 실제 초유지 · 흡수 · 통째로 되돌림

흔한 오해가 있다 — "코드가 하나로 세니까 모델이 못 나눈다". 반대다. 모델은 나누고, 코드가 그걸 되돌린다. 모델은 자기가 본 세션 하나만 아는지라 나눔의 대가를 모른다(레벨·갈래·지도·성격이 따라 움직이는 것). 그 대가를 아는 쪽이 코드다.

① 모델이 내는 것

실제 세션(2026-08-07 12:21, 241분)에서 나온 출력이다.

{
  "summary": "Project NA 데이터베이스 테이블을 검토하고 로컬 환경에서…",
  "segment_ids": [0,2,3,4,5,7,8,9,10,11,12,13,14],

  "also": [
    { "summary": "SOLDIER: A DAY 게임을 테스트했다.",
      "segment_ids": [6] }        ← 6번 구간 하나. 실제 7분
  ]
}

판단은 옳다 — SOLDIER : A DAY 는 정말 다른 프로젝트이고 6번이 맞는 구간이다.

② 코드가 재는 것

먼저 — 아래 중 하나라도 걸리면 통째로 안 나눈다
· 구간 번호가 범위 밖이거나 두 경험에 겹쳐 배정됐다
· 갈라진 것에 배정이 하나도 없다 (시간을 잴 수 없다)
· 구간 시간의 총합이 0 (sec 이 없던 옛 세션)

통과하면 — 갈래마다 따로 판정
· 문턱 7분 미달 → 버리지 않고 주 경험에 흡수
· 최대 3개, 넘치면 오래 머문 것부터
· duration_min = 세션 길이 × (그 구간들의 초 / 전체 초)

같은 출력에 문턱만 달리 대면 결과가 갈린다.

문턱 10분   7분 < 10분 → ✗ 흡수
             곁가지 summary 가 주 경험 detail 뒤에 붙는다
             스킬이 주 경험에 합쳐진다
             6번 구간도 주 경험이 가져간다
             → 경험 1건. "SOLDIER" 는 문장으로만 남는다

문턱  7분   7분 ≥ 7분  → ✓ 유지
             → 경험 2건. SOLDIER 가 제 경험이 되고 제 갈래를 갖는다

흡수는 삭제가 아니다

문턱을 못 넘겨도 정보는 남는다. 요약 문장은 주 경험의 detail 로, 스킬은 스킬 목록으로 합쳐진다. 일기에도 그 문장이 들어간다. 사라지는 것은 "한 건"이라는 카운트뿐이다.

왜 회계를 코드가 갖고 있나

경험 하나로 세는 순간 다섯 군데가 따라 움직이는데, 경험을 다시 합치는 수단이 없다.

따라 움직이는 것어떻게
레벨1 + floor(√(경험수 × 스킬수)) — 잘게 쪼갤수록 부푼다
갈래모든 경험은 갈래를 갖는다. 3분짜리도 갈래를 하나 만든다
지도그 갈래가 별 하나로 뜬다
성격개척형 축이 is_first_time 비율이라 분모가 바뀐다
프롬프트"최근 경험 3건" 창을 3분짜리가 차지한다

갈래는 반대 방향이다 — "애매하면 new". 잘못 붙이면 영영 못 떼지만 잘못 나누면 사람이 합칠 수 있어서다. 경험은 그 되돌릴 장치가 없어서 반대로 보수적이다.

문턱은 왜 7분인가

10분이었다. 전송 필터의 "10분 미만" 을 그대로 가져온 값인데 성격이 다르다 — 저쪽은 세션 하나를 통째로 버리는 문턱이고 여기는 이미 있는 세션 안에서 나누는 문턱이다. 241분 안의 7분짜리 다른 프로젝트를 "너무 짧다"고 볼 이유가 저쪽에는 있고 이쪽에는 없다.

실세션 18건에서 같은 모델 출력 위에 문턱만 바꿔 쓸었다. 매번 LLM 을 다시 부르면 출력이 흔들려 문턱 효과와 구분되지 않으므로, 출력을 캐시하고 판정만 재계산한다(probe-threshold.mts).

문턱경험 총수새로 갈라지는 것
10분27건—
7분30건전부 긴 세션에 묻혀 있던 다른 프로젝트 (241분 안의 SOLDIER 7분)
5분32건62분 세션의 5분짜리 곁다리가 섞이기 시작
3분38건1분짜리까지 경험이 된다 — 경유지지 경험이 아니다

7분에 근거가 하나 더 있다: 압축기가 1분 미만 구간은 칸을 안 주고 접으므로(FOLD_UNDER_SEC), 살아남은 구간은 이미 "1분은 머문 곳"이다. 그게 몇 개 모여 7분이면 스쳐간 것이 아니다.

바꾼 뒤 재구축에서 경험 25 → 28, 갈래 5 → 8이 됐고 SOLDIER: A DAY·대한항공 마일리지 활용 같은 것들이 처음으로 제 갈래를 얻었다.

빈 배열의 뜻

주 경험의 segment_ids가 빈 배열이면 "세션 전체"다. 그래서 갈라져 나간 몫만 빼고 나머지를 전부 갖는다. 배정 안 된 구간의 몫은 어느 경험에도 안 간다 — 세션은 관측이고 경험은 해석이라, 해석이 관측 전부를 덮을 필요가 없다. "197분 중 설명되는 건 27분" 이 사실 그대로다.

여기서 한 번 크게 데었다 — 흡수할 때 곁가지 번호를 주 경험에 그냥 push 했더니, 전체를 뜻하던 빈 배열이 곁가지 크기로 쪼그라들었다. 130분 세션의 주 경험이 5분짜리가 되고 77분이 아무 경험에도 안 들어갔다. 지금은 빈 배열이면 전체에서 갈라진 몫만 빼는 방식으로 계산한다.

마지막 — 저장

정제가 끝난 것을 트랜잭션 하나에 쓴다. 순서에 이유가 있다.

BEGIN
  ① update sessions set processed_at = now()
       where id = ? and processed_at is null     ← 0행이면 throw (아래 참고)

  경험마다 반복 (1~3건)
  ② insert threads          action='new' 일 때. FK 때문에 경험보다 먼저
  ③ insert experiences      summary·detail 은 자르지 않는다
  ④ insert experience_skills
  ⑤ upsert user_skills      points 누적 · domain 은 최빈값 재계산
                            last_used_at 은 GREATEST — 역행 방지
  ⑥ update threads          action='attach' 일 때. last_activity_at GREATEST,
                            experience_count +1, abandoned→active, category 재계산
  ⑦ upsert memories         문턱 60 넘거나 갈래 6건째면. 갈래당 하나에 근거를 더한다

  세션에 한 번
  ⑧ upsert dialogues × 4    슬롯당 하나. 80자로 잘라서
  ⑨ update characters       경험 수·스킬 수·레벨·기억 수·oldest_memory_at
COMMIT

왜 이 순서인가

자리이유
① 이 맨 앞처리 권리를 선점한다. 뒤에 두면 두 실행이 나란히 LLM 을 부르고 둘 다 저장한다
② 가 ③ 보다 먼저experiences.thread_id 가 FK 다 — 참조 대상이 있어야 통과한다
⑦ 이 ⑥ 뒤기억의 중요도가 갈래에 쌓인 경험 수를 쓴다. 갱신 전 값을 쓰면 하나씩 적게 센다
⑧ 이 루프 밖대사는 슬롯당 하나라 세션 단위다. 경험이 셋이어도 4개다
⑨ 가 맨 끝레벨이 √(경험수 × 스킬수) 라 앞이 다 끝나야 맞다
트랜잭션 밖에도 하나 있다 — llm_outputs 는 검증 전에, 트랜잭션과 무관하게 쓴다. 그래야 검증 실패분(valid=false)과 롤백된 판정까지 남는다. 로깅 실패가 처리를 막으면 안 되므로 예외를 삼킨다.

중복 처리를 막는 법

트랜잭션 맨 앞에서 처리 권리를 선점한다.

update sessions set processed_at = now()
 where id = ? and processed_at is null

0행이면 이미 다른 실행이 가져간 것이므로 예외를 던져 롤백한다(return은 롤백이 아니라 "건너뛰고 커밋"이다). 예전에는 experiences.session_id의 UNIQUE가 이 방어를 겸했는데, 한 세션에서 경험이 여럿 나올 수 있게 되며 그 제약을 풀었다.

잘린 답을 조용히 받지 않는다

also는 출력 끝에 오는데 스키마상 optional이라, 상한에 걸려 잘려도 검증을 통과한다 — 경험이 조용히 하나로 줄어든다. 필수 필드는 앞에서 이미 채워졌으니 겉보기엔 멀쩡한 판정이다. 실제로 그렇게 몇 달을 돌았다.

temp=0 max_tokens=2000 → 경험 3·3·3   stop=tool_use
temp=0 max_tokens=1024 → 경험 3·1·1   stop=max_tokens

상한을 2048로 올리고, stop_reason === 'max_tokens'면 검증을 통과했더라도 실패로 처리한다. 조용히 틀리는 것보다 드러나는 편이 낫다.

temperature: 0인 이유도 실측이다 — 기본값 1.0으로는 같은 세션을 두 번 돌리면 outcome이 4/7건 흔들렸다. 대사(창작)도 같은 호출에 섞여 있지만 흔들려선 안 되는 쪽을 우선한다.

검증이 폐기가 되면 안 된다

대사 한 줄이 81자면 zod가 출력 전체를 반려했고, 멀쩡한 summary·category·outcome·skills까지 통째로 버려져 그 세션은 경험이 되지 못했다. 대사는 파이프라인에서 가장 안 중요한 값 (슬롯당 1행씩 덮어써지는 캐시)인데 그게 가장 중요한 값을 죽였다.

지금은 자를 수 있는 건 자르고(문장 경계에서), 개수도 강제하지 않는다. 부족한 슬롯은 이전 대사가 남아 있으면 그걸로 버틴다.
08

갈래와 기억

갈래 — 같은 대상을 계속 다룬 것

분야가 같다는 것은 붙이는 근거가 아니다. 같은 저장소, 같은 기능, 같은 문서, 같은 버그, 같은 강의여야 한다.

애매하면 새로 만든다. 잘못 붙이면 영원히 안 갈라지지만, 잘못 나누면 나중에 합칠 수 있다.

모든 경험은 갈래를 갖는다 — attach 아니면 new고, 모델이 목록에 없는 id를 지어내면 new로 강등한다.

후보를 어떻게 고르나

몫수기준
최근 활동순8진행 중 갈래
어휘 겹침 (추가)3최근순에서 밀려난 것만
잠긴 갈래330일 넘게 손 안 댄 것 중 어휘가 겹치는
어휘 검색이 왜 필요했나 — 최근순만 주면 조용했던 갈래는 딱 맞아도 눈에 안 띈다. 프롬프트가 "목록이 비었으면 무조건 new"라고 하니 모델은 규칙대로 새로 만들고, 그 새 갈래가 최근순 위쪽을 차지해 원래 갈래를 더 밀어낸다. 실측으로 ai 분야 세션 둘이 각각 새 갈래를 만들었는데, 이미 "AI 도구 활용법 탐색"이 있었고 마지막 활동이 사흘 전이라 6·7위로 밀려 후보에 없었다.

매칭은 Postgres가 한다. 갈래 쪽에 키워드를 저장하지 않고, 이미 있는 글(threads.title과 그 갈래에 붙은 experiences.summary)을 GIN 인덱스가 색인한다 — 어긋날 파생값을 늘리느니 인덱스가 낫다. 도메인은 안 쓴다 — github.com은 모든 dev 갈래에 겹쳐 변별력이 없다.

붙을 때 갱신되는 것

last_activity_at  GREATEST(기존, 새것)  ← 역행 방지
experience_count  +1
status            abandoned 였으면 active 로 (무덤이 아니라 잠금이다)
category          속한 경험들의 최빈값으로 다시 계산
title             안 바꾼다

completed는 안 건드린다 — 사람이 선언한 값이라 모델이 뒤집으면 위계가 거꾸로 선다.

제목은 왜 안 바꾸나 — 갈래는 정의상 같은 대상이라 이름이 낡아도 대상은 맞다. 내용 최빈값으로 다시 지으면 오배정된 경험이 제목을 끌고 가고, 바뀐 제목이 다음 세션을 더 끌어당긴다. 실측된 연쇄 오염이 정확히 그 모양이었다. 안 바뀌는 것이 닻이다.

기억 — 갈래에 남은 것

갈래가 그릇이고, 기억은 그 안에 든다.

갈래당 기억은 하나다. 조건을 또 넘기면 새로 만들지 않고 experience_ids에 근거를 더한다.

예전에는 조건을 넘길 때마다 따로 생겨서 같은 갈래에 기억이 셋씩 붙었다(실데이터: 경험 9건 → 기억 3개). 셋은 결국 같은 주제인데 제목만 다르고, 셋 다 누르면 같은 위성 9건이 떴다 — 기억의 근거가 "자기 경험 + 같은 갈래 경험 전부"였기 때문이다. 새벽 2시 기억이 4시간 뒤 경험까지 근거로 보여주는 셈이었다.

점수 — LLM 없이 규칙으로

규칙점수판정 기준
신규 스킬 등장+50user_skills에 없던 이름 (코드가 확정)
첫 시도+40is_first_time
막힘 → 성공+35직전이 stuck인데 이번이 success
공백 후 복귀+30직전 경험과 3일 이상
묵힌 스킬 재등장+2530일 이상 안 쓴 스킬
평소보다 긴 세션+20최근 20개 평균의 2배
같은 패턴 반복−30최근 3건과 분야·주요 스킬이 모두 같음

60점 이상이면 기억이 된다. 아래 둘은 점수와 무관하게 기억을 만든다.

트리거조건제목의 출처
deepened갈래에 경험이 정확히 6건째갈래 제목
thread_complete사람이 지도에서 끝을 누름갈래 제목
점수 60↑new_skill·breakthrough·revival·comeback경험 요약

출처가 갈리는 게 규칙이다. 점수 트리거는 그 순간이 특별해서 터진다 — 제목이 그 순간을 가리켜야 한다. 22건짜리 갈래의 15번째 경험에서 new_skill이 터졌는데 제목이 두 달 전 갈래 이름이면 왜 남았는지 한 마디도 안 하는 셈이다. 반면 deepened· thread_complete는 갈래에 대한 진술이라 갈래 제목이 맞다.

문턱을 80에서 60으로 내린 이유 — 80이었을 때는 "신규 스킬 + 첫 시도"가 겹치는 경우 말고는 넘을 길이 사실상 없었다(50/40/30/20 조합상 두 개가 겹쳐야 도달). is_first_time이 잘 안 뜨면 그 유일한 길마저 막혀서 하루 여섯 경험에 기억 0건이 나온다. 60이면 신규 스킬 하나만으로는 여전히 부족하지만(50) 거기에 뭐라도 하나 겹치면 남는다.

deepened를 넣은 이유 — 매 세션은 특별할 게 없는데 몇 달째 이어지는 갈래에 기억이 하나도 안 생기던 구멍을 메운다. 문턱 6은 6개월치 분포의 상위 21%(평균 3.5건)이고, === 6이라 자연히 한 번만 발동한다.

thread_complete가 사람 몫인 이유 — 모델이 못 내는 값이었다. 역대 LLM 호출 75회 중 completed=true가 한 번도 없었고, 프롬프트가 완결 예시로 못 박은 세션을 그대로 재현해도 false였다. 브라우징 기록은 "무엇을 했나"를 말하는데 완결은 "더 할 게 없다"는 판단이라 안 한 일에 대한 진술이어서 기록에 흔적이 없다.

중요도는 매번 다시 잰다

importance = clamp(가장 센 근거의 점수)
           + floor(근거 수 / 2)
           + floor(갈래 경험 수 / 6)          → 1~10

예전에는 붙을 때마다 max(기존, 새것) + 1이라 올라가기만 했다. 교정으로 근거 점수가 낮아져도 안 내려가서 오래 살아남은 기억은 전부 10에 수렴했고, +1이 근거의 세기와 무관해 20점짜리 여덟 개가 110점짜리 하나보다 무거웠다.

occurred_at은 근거가 늘어도 안 건드린다 — 그 일이 처음 남을 만해진 순간이고, 지도의 반경(나이)이 그 값이라 덮으면 오래된 일이 최근으로 보인다.

사람이 고치는 길

모델 출력을 다시 학습시키면 그 모델을 복제할 뿐이다.

experiences·dialogues·daily_logs가 전부 LLM 생성물이라, 그것만으로는 1년 뒤 데이터셋을 뽑아도 쓸모가 없다. 사람의 판단이 들어오는 통로를 따로 냈다.

두 층

층어디서성격
1 교정 칩/diary의 각 경험훑다가 눈에 띄면 고친다
2 캐릭터 질문홈 화면모델이 제일 자신 없는 자리를 골라 먼저 묻는다

고칠 수 있는 것은 outcome·category·is_first_time 셋. 이산값만 받는다 — 자유 서술은 학습에 바로 못 쓴다.

왜 테이블이 둘인가

테이블담는 것
corrections사람이 실제로 내린 판단. 행이 있으면 반드시 답이 있다
questions캐릭터가 던진 질문과 그 결말. 침묵도 기록한다
하나로 합치면 human_value가 NULL인 행이 "안 물어봤다"인지 "묻고 답을 못 받았다"인지 구분되지 않는다. 무응답을 동의로 세면 데이터가 조용히 오염된다 — 무응답은 대개 동의가 아니라 안 본 것이다. 그래서 answered_at·dismissed_at이 둘 다 NULL인 행이 침묵이고, "모르겠어"로 넘긴 것(dismissed_at)과도 구분한다.

append-only인 이유

같은 필드를 두 번 고치면 두 행이 쌓이고 최신 행이 이긴다. 덮어쓰면 (모델 출력, 사람 정답) 쌍이 사라지는데, 학습에 필요한 건 정답이 아니라 그 쌍이다. 한 번에 확정한 교정과 세 번 뒤집은 교정은 라벨 신뢰도가 다른데, 덮어쓰면 그 구분이 사라져 1년 뒤 둘 다 그냥 정답으로 보인다.

model_value는 참조가 아니라 사본이다 — 재처리로 experiences 값이 바뀌어도 쌍이 보존돼야 한다.

다만 같은 값을 두 번 눌러도 행이 쌓이지는 않는다. 그건 이력이 아니라 잡음이다. 값이 실제로 달라졌을 때만 새 행을 만든다.

고치면 무슨 일이 일어나나

corrections 에 append
   ↓
① 화면          읽을 때 겹친다  experiences 는 UPDATE 하지 않는다
② 프롬프트      [사람이 고침] 표시 + 교정 패턴 집계
③ 기억 재판정   점수가 60을 넘으면 기억을 만든다
④ 감정          교정된 outcome 으로 다시 계산
③이 없으면 교정이 라벨 더미가 된다 — memory_score는 엔진이 세션을 처리하는 그 순간에 계산해 저장한다. 교정은 그 뒤에 들어오고 읽을 때만 겹쳐지므로, 고쳐도 점수는 그대로였다. is_first_time을 true로 바꾸면 +40이라 20점짜리가 60을 넘는데(실데이터에 정확히 그런 경험이 3건) 아무 일도 안 일어났다.

전체를 다시 계산하지 않는 이유 — 점수 항목 중 셋은 "그때의 상태"에 달려 있다(보유 스킬, 마지막 사용 시각, 최근 세션 평균). 오늘 다시 재면 다른 값이 나온다. 전체 재계산은 과거를 오늘 기준으로 다시 쓰는 일이다. 그래서 교정으로 바뀔 수 있는 항목만 전/후로 구해 차이만 더한다.

④가 없으면 아무도 안 누른다 — "이건 막힌 게 아니라 해낸 거야"라고 세 건을 고쳤는데 홈의 캐릭터가 계속 답답해하면 고쳐도 아무것도 안 달라지는 것이고, 그러면 declared가 쌓이지 않는다.

캐릭터 질문 — 예산과 로테이션

값수왜
하루 예산2한꺼번에 들이밀지 않는다. 답하면 다음 것이 나타난다
동시에 열린 질문2안 답한 게 쌓이면 전부 무시하게 되고 침묵률만 올라간다
후보 기간3일2주 전 판정을 물으면 답이 추측이 된다 — 그건 또 다른 inferred다

필드 로테이션이 없으면 category는 영원히 차례가 안 온다. 실측 12건에서 outcome='explore'가 절반이었다 — 순위표 하나로 세 필드를 겨루게 하면 explore 대기열이 비지 않아 나머지가 굶는다. 날짜로 짝을 고정해 3일 중 2일씩 돌아가게 한다.

무엇을 먼저 묻나 — 모델이 준 확신도가 아니다. Haiku는 logprob을 안 주고 자기보고 confidence는 보정이 안 돼 오히려 나쁘다. 대신 프롬프트가 "판단이 안 설 때 쓰는 값"이라고 직접 규정한 자리(explore, etc, search)와 실측에서 흔들린 자리를 쓴다.

질문 생성은 야간 배치가 한다. 페이지 렌더에 두면 서버 컴포넌트가 매 렌더마다 쓰기를 하게 되고, "하루 N건" 예산을 새로고침 횟수가 좌우하게 된다.

2가 1 다음 — 일기는 그날 경험을 읽지 기억을 안 읽으므로 순서 의존이 없고, 기억 본문이 바뀌기 전에 일기가 먼저 쓰이는 편이 낫다.
6이 마지막 — 앞 단계가 그날 경험을 다 반영한 뒤라야 후보가 온전하고, 실패해도 일기·성격· 레벨에 영향이 없다(질문은 있으면 좋은 것이지 필수가 아니다).

하루의 경계 — 새벽 4시

자정이 아니다. 새벽 0~3시대 활동은 "어제 밤"의 연장이다. 이 정의에 daily_logs.log_date, 갈래 무활동 판정, 활동일 수, 성격의 새벽형 축, 화면의 "오늘"이 전부 매달려 있다.

배치가 3시에 도는 것과 경계가 4시인 것이 충돌한 적이 있다 — 이 시각의 "어제"는 이미 그저께라서, 어젯밤에 쌓인 경험들이 일기를 영영 못 받는 off-by-one이 났다 (실측: 8/5 03:00 실행이 8/3을 겨냥). 지금은 "지금 끝나가는 하루"를 겨냥한다.

남은 한계 — 정규 실행(3시) 후 3~4시 사이에 닫힌 세션은 그날 일기에 못 들어간다. 자정 대신 3시를 택하며 수용한 트레이드오프다.

KST 규칙은 @na/shared/kst.ts 한 곳에만 있다. 예전엔 웹과 배치에 두 벌이었는데, 규칙이 같아 보여도 두 벌이면 한쪽만 고쳐지는 날이 오고 그때부터 일기에 안 들어간 세션이 화면에는 오늘 것으로 뜬다.

캐릭터 — 감정·레벨·성격

감정 — 저장하지 않는다

emotions 테이블이 없다. 조회 시점의 최근 경험 5건에서 매번 계산하는 순수 함수다.

위에서부터 먼저 만족하는 규칙이 이긴다
① 최근 48시간 안에 처음 해본 것이 있다   → 흥분
② 가장 최근 3건이 연달아 stuck            → 답답
③ 직전 경험과 3일 이상 공백               → 반가움
④ 30일 이상 안 쓴 스킬이 이번에 재등장      → 그리움
   해당 없음                              → 평온

가장 최근 경험이 48시간보다 이전이면 규칙과 무관하게 평온

저장하면 "3주 전의 기쁨"이 남는다. 시간이 지나면 자연히 평온으로 감쇠하는 것이 맞다.

①에 시간 창이 필요했던 이유 — 표본 전체를 훑으면 경험이 드문 사용자는 몇 달 전의 첫 시도 하나로 감정이 영구히 '흥분'에 고정된다. 3일 만에 돌아온 오늘도 '반가움'이 아니라 '흥분'이다. is_first_time을 관대하게 판정하도록 바꾼 뒤로 더 잘 걸린다.

레벨

레벨 = min( 1 + floor(√(경험 수 × 고유 스킬 수)),
            floor(가입 후 일수 / 3) + 1 )

학습량이 레벨을 올리고, 일수는 하루 몰아치기를 막는 브레이크로만 쓴다. 일수가 단독 변수면 방치 계정이 Lv.60 "동료 AI"가 되어 정의가 깨진다.

공식은 @na/shared/level.ts 하나를 엔진과 배치가 함께 쓴다 — 두 곳에 복붙하면 실시간 레벨과 배치 후 레벨이 어긋난다. 어긋남 다만 인자가 갈려 있다(16장).

성격 — 다섯 축

최근 14일 세션이 10개 이상인 유저만 대상. 그 14일 창 자체가 이동평균 역할을 해서 세션 하나로 축이 요동치지 않는다. 갱신이 아니라 append다.

축관측값방향
몰입형 ↔ 산만형세션 평균 길이, scattered 비율길수록 +, 산만 비율만큼 −
집중형 ↔ 멀티형세션당 unique_domains적을수록 +
완결형 ↔ 탐색형갈래 completed / (completed + abandoned)비율 0.5가 중립
개척형 ↔ 숙련형is_first_time 비율높을수록 +
새벽형 ↔ 아침형세션 시작 시간대 분포0~6시 비중 − 6~12시 비중

완결형 축만 전 기간을 집계하던 버그가 있었다 — 다른 넷은 전부 14일 창을 보는데 이 축만 안 걸어서, 1년 전에 끝낸 작업 40개가 분모에 남아 최근 두 달을 전부 흘려보낸 사람도 완결형(+67)으로 고착됐다. "매일 밤 최근 14일을 다시 계산해 append"라는 선언과 어긋나 있었다.

캐릭터 캐시

characters의 숫자는 전부 파생값이다. 엔진이 세션 처리 때 증분으로 올리고, 밤 배치가 원본에서 다시 세어 바로잡는다. 툴 게이팅이 JOIN 없이 한 행만 읽도록 모아둔 것이다.

활동일 수는 24로 나누면 안 된다 — 밤 11시에 가입한 사람은 다음날 밤 10시가 되어도 0일이라 레벨 상한이 1에 묶인다. 표시가 아니라 실제 레벨을 깎는다. "며칠째"는 흐른 시간이 아니라 넘어온 날 경계의 수를 묻는 말이다.

진입 시 LLM 호출 금지. 세션 마감 때 시간대별 대사 4개를 미리 만들어두고, 홈은 현재 슬롯 1행만 읽는다.

네 슬롯이 전부 같은 세션을 말한다 — 아침에 열어도 그 대사는 어젯밤 세션에서 나온 것이다. 시간대별 어감을 미리 준비해두고 꺼내 쓰는 방식이라 내용은 최신 세션 하나에 매인다. 의도한 트레이드오프다.

확장 팝업

네트워크를 안 쓴다. 서버에 아직 가지 않은(어쩌면 영영 가지 않을) 상태를 보는 것이 목적이고, 그 진실은 전부 로컬 IndexedDB에 있다.

  • 지금 마감되면 — 전송될지 버려질지, 버려지면 사유까지
  • 남은 시간 — idle · maxlen · 날짜 경계까지
  • 버려진 것들의 내역 — 탈락 사유 + 마감 사유를 함께. '10분 미만'이 switch로 잘린 앞 조각이면 끊는 규칙이 작업을 죽인 것이고, 그냥 잠깐 훑고 만 것이면 버려지는 게 맞다

팝업을 열어보는 행위가 데이터에 영향을 주지 않는다 — 읽기만 하고 세션 판정을 앞당기지도 않는다.

설명이 필요한 결정

sessions.id를 클라이언트가 만든다

서버 생성 UUID면 재시도 시 같은 세션이 두 번 들어간다. 클라이언트 UUID를 PK로 두면 ON CONFLICT DO NOTHING 한 줄로 멱등성이 끝난다.

emotion 컬럼 대신 outcome

success / partial / stuck / explore 넷이 감정의 재료다. 감정은 시점에 따라 달라지는 파생값이라 저장하지 않는다.

memories.experience_ids에 FK가 없다

배열 컬럼에는 참조 무결성을 못 건다. 경험을 지우는 건 재구축뿐이고 그때 기억도 함께 지워지므로 실무상 문제가 없다.

memories.forgotten_at은 삭제가 아니라 마킹

데이터는 남고 검색 결과에서만 빠진다. 성능 최적화가 서사와 일치하는 드문 지점이다. 미구현 — 읽는 쪽은 다 있는데 세우는 코드가 없다.

llm_outputs가 따로 있는 이유

ingest_failures는 "실패"만 남긴다. 그래서 성공한 판정의 근거가 어디에도 없었다 — outcome이 왜 explore였는지 나중에 물으면 세션을 다시 LLM에 태우는 것 말고 답할 방법이 없었고, 비교 대상인 이전 출력은 이미 가공된 뒤였다.

assertion class

declared  사람이 선언한 것    corrections · questions · 갈래 완결
observed  센서가 본 것        sessions · Storage 원본
inferred  모델이 추론한 것     experiences · dialogues · daily_logs · memories

충돌하면 declared > observed > inferred

이 위계가 프롬프트에도 그대로 들어간다. 안 적으면 모델이 사람이 고쳐놓은 값을 자기 추론으로 다시 덮는다.

스키마의 진실은 SQL이다

supabase/migrations/*.sql이 정본이고, packages/db/src/schema.ts는 그걸 타입 안전하게 다시 표현한 것일 뿐이다. drizzle-kit으로 마이그레이션을 만들지 않는다 — 컬럼을 고치려면 SQL을 먼저 쓰고 손으로 동기화한다.
