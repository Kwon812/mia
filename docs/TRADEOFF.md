# 트레이드오프 — 실측 기준

2026-08-09. 추정이 아니라 잰 값에서 시작한다.

## 지금 (기준선)

```
세션 20개 · 경험 27건 · 5일 · 하루 4세션
DB 13.0MB / 500MB (Supabase 무료)
압축로그 세션당 1,972B
LLM 세션당 1회 · 호출당 $0.0147
```

가장 큰 표가 `llm_outputs` 680KB(325행)다. 세션이 20개인데 행이 325개인 건
재구축을 여러 번 돌려서다 — 재구축 한 번이 세션 수만큼 행을 더한다.

**주의**: 표 크기(352KB/20행)로 행당 크기를 역산하면 안 된다. 이 규모에서는
페이지·인덱스 고정 비용이 대부분이다. 아래 추정은 실제 컬럼 크기로 한다.

## 저장 — 1년치 (하루 4세션 = 1,460세션)

| | 세션당 | 1년 | 비고 |
|---|---|---|---|
| 압축로그 (지금) | 2KB | **2.9MB** | |
| 압축로그 + 조작 | 10~30KB | **15~44MB** | |
| 조작 **최악** | 38KB | **56MB** | 상한이 걸려 있다 |
| llm_outputs | 2KB | 2.9MB | 세션당 1행 |

**최악이 계산된다는 게 핵심이다.** 상한을 코드에 박아뒀다:

```
MAX_ACT           40   한 틱(10초)에 남길 조작
MAX_SEGMENT_ACTS  24   구간당 조작
MAX_SEGMENTS      20   세션당 구간
→ 세션당 최대 480조작 × 약 80B = 38KB
```

무한정 늘어나는 항이 없다. 자동 스크롤이 도는 페이지에 하루 종일 있어도
세션당 38KB에서 멈춘다.

**500MB까지 8~17년.** 저장은 제약이 아니다.

진짜 위험은 용량이 아니라 다른 데 있다:
- 무료 플랜은 **1주 미사용 시 프로젝트를 잠재운다** — 쓰다 말면 이게 먼저 걸린다
- 재구축을 자주 돌리면 `llm_outputs` 가 세션 수만큼 곱해져 쌓인다 (지금 325행)

대신 그날 바로 해석이 안 나온다.

## 성능 — 브라우저

조작 기록은 클릭마다 돈다. 재보니 항목별로 무게가 다르다.

| | 비용 | 판단 |
|---|---|---|
| `closest()` · `getAttribute()` | 마이크로초 | 무시 가능 |
| `textContent` | 마이크로초 | 무시 가능 |
| **`innerText`** | **레이아웃 강제 계산** | 위험 |

`innerText` 는 "화면에 보이는" 텍스트라 스타일·레이아웃을 다시 계산하게
만든다. 클릭 한 번에 한 번이면 사람 눈에 안 보이지만, 무한 스크롤이나
드래그처럼 클릭이 연달아 오는 화면에서는 끊김으로 드러난다.

`textContent` 를 먼저 쓰고 비었을 때만 떨어진다 — 라벨 정확도를 조금 잃고
(숨은 요소의 텍스트가 섞일 수 있다) 끊김을 없앤다. 절차 추출에는 그 정확도가
필요 없다: 버튼 라벨은 대개 자식 노드 하나뿐이라 둘이 같은 값을 낸다.

## 사람의 시간

이게 제일 비싼 자원인데 가장 안 재진다.

| | 손이 가는 정도 | 얻는 것 |
|---|---|---|
| 갈래 교정 | 하루 1~2번 (실측: 40세션에 5~15번) | F1 54 → 60~88 |
| 스킬 후보 승인 | 며칠에 한 번 | 틀린 후보가 안 쌓인다 |
| 4시 배치 | **0** | F1 개선 (측정 안 함) |

교정은 **초반에 몰린다** — 새 프로젝트가 처음 나타날 때 한 번 손이 가고
그 뒤로는 갈래가 자리를 잡는다. 즉 횟수는 프로젝트 개수에 비례하지
세션 개수에 비례하지 않는다. (이건 추론이다. 시점 분포는 안 재봤다.)

## 한 줄 요약

쌓이기까지의 며칠**. 둘 다 돈으로 못 산다.
